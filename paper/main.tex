\Title{Spatio-Temporal Provenance Guard: Detecting Privilege Escalation Attacks that Exploit Spatio-Temporal Data Loss in Multi-Agent MCP Environments}

\newcommand{\orcidauthorA}{0000-0002-3740-5568}
\newcommand{\orcidauthorB}{0000-0001-6931-2705}
\Author{Deuk-Hun Kim $^{1}$\orcidA{} and Jin Kwak $^{1,*}$\orcidB{}}

\address{%
$^{1}$ \quad Department of Cyber Security, Ajou University, Suwon 16499, Gyeonggi-do, Republic of Korea; kimdh1206@ajou.ac.kr (D.-H.K.); security@ajou.ac.kr (J.K.)}
\corres{Correspondence: security@ajou.ac.kr}

\abstract{When systems using the Model Context Protocol (MCP) lose provenance across storage and session boundaries, fragmented records can induce privileged transfers. We propose Spatio-Temporal Provenance Guard (STPG), a gateway defense that preserves source provenance and authorizes routing destinations through reference resolution, a semantic witness, and deterministic support-path verification. Comparisons use evidence adapters on a common kernel, not implementations of published defenses. On Google Cloud with Gemini agents, STPG blocked 648/648 attack calls and passed 69/71 approved transfers; the two blocked transfers had malformed destinations. Per-record and source-lineage grouping produced identical gate decisions on the sets included in the ablation, so assembly did not improve blocking there. Robustness and Llama 4 Maverick sensitivity studies exposed limitations in identifier handling, notice interpretation, reference resolution, and trusted rewrites. On a set generated with second-family phrasings after kernel v3.4 and witness prompt w3 were frozen, STPG matched the specified decision in 190/260 counterfactual calls, and the later v3.5 identifier contract left these decisions unchanged. These results support bounded, destination-level enforcement on the evaluated synthetic data and distinguish enforcement from read-time detection; they do not establish complete protection or generalization to untested deployments.}

\keyword{multi-agent systems; Model Context Protocol; data provenance; privilege escalation; AI security}

\section{Introduction}
\label{sec:intro}

LLM (Large Language Model) agents have moved from a single agent that calls tools to systems in which several agents with separate roles cooperate \cite{wang2024agents,xi2025rise}. MCP (Model Context Protocol) standardizes how an agent discovers and invokes tools, reads data sources, and exchanges state \cite{mcpspec}; MCP-based multi-agent deployments are proposed for security operations \cite{mcpsoc2026}, and the cloud operations they serve are increasingly monitored under zero-trust frameworks \cite{mcloudzt2026}. Interconnection enlarges the attack surface: inter-agent messages, shared stores, delegated privileges, and untrusted content that enters through ingestion paths become points of entry, and indirect prompt injection \cite{greshake2023}, the confused-deputy problem first described by Hardy \cite{hardy1988}, and privilege escalation are among the core threats to agent systems \cite{agentsurvey2026,yao2024survey}.

This paper studies one property of such systems as an attack enabler: data accumulates across storage boundaries and sessions, and the metadata that would tell a later reader where a record came from is normally not stored with it. We call provenance loss at storage and session boundaries spatio-temporal data loss: the records persist, but their provenance does not. The loss has a spatial dimension, the dispersion of records over injection locations and stores (a log message, a ticket description, an API (Application Programming Interface) description field, each read through a different path), and a temporal dimension, the dispersion over sessions that have ended by the time the record is read. An adversary who controls only an ingestion path can exploit both without writing a complete instruction anywhere: the parts of an outbound-transfer directive are placed in several records that each read as an operational note. When a high-privilege agent later reads the records of a domain into one context, the directive emerges and the agent forwards data to an external destination under its own privilege.

Two questions follow for a defense. The first is whether such an induced transfer can be stopped; in the configurations we evaluate, a gate that keeps provenance across the storage boundary and refuses an external transfer unless a trusted directive authorizes it does so. The second is whether such a gate can be deployed on a path that legitimately reads untrusted data: operations agents read intake notes, vendor advisories, and imported registries as a matter of course, and operators issue approved external transfers such as a standing rule that forwards a weekly report to a partner. A gate that blocks any untrusted influence can reject legitimate operations. A gate that treats a trusted mention as authorization can permit transfers supported only by a registry mention or explicitly prohibited by a rule. The defense therefore has to answer, at the moment of the call, which records formed the directive behind it, whether that directive targets this destination, and whether it was authorized: the distinction between provenance and authorization that AuthGraph draws for single executions \cite{wang2026authgraph}, carried across the storage boundary and conditioned on the destination.

We propose STPG (Spatio-Temporal Provenance Guard), a defense inserted into the MCP gateway. PPT (Persistent Provenance Tagging) attaches a provenance sidecar, a metadata record stored alongside the data record, to every record at write time, keyed by the authenticated source connector, so that lineage survives both boundaries. TSA (Temporal Shard Assembly) regroups, at read time, the records that share a lineage regardless of location and session, reassembles them, and scores whether the assembled text forms an external-transfer directive. PDG (Privilege-Delta Gate) binds the destination of the actual call to the lineages that name it, directly or through registry references, asks a destination-conditioned witness whether a binding lineage targets that destination, verifies the verdict against a deterministic support path, and applies one kernel: pass on a trusted directive, block on an untrusted one, block by default. Absence of detection is not treated as authorization.

STPG contributes a threat model for incomplete untrusted records assembled across storage and session boundaries, a gateway mechanism for persistent provenance and destination-specific authorization, and an evaluation that separates attack blocking, approved-transfer preservation, attribution, and operating cost. The comparisons concern evidence adapters on a common kernel. The evaluation includes grouping ablations, a second model family, adverse reference and identifier cases, and an additional set of model-written phrasings; that set was generated after kernel v3.4 and the witness prompt were frozen, and the effects of the later v3.5 identifier contract are reported separately.

The remainder of this paper is organized as follows. Section~\ref{sec:related} reviews related work. Section~\ref{sec:problem} analyzes the problem and the limitations of existing defenses. Section~\ref{sec:improve} derives the improvements and hypotheses. Section~\ref{sec:method} presents the proposed method, STPG. Section~\ref{sec:exp} describes the experimental setup. Section~\ref{sec:results} reports the experimental results. Finally, Section~\ref{sec:conclusion} concludes the paper.

\section{Related Work}
\label{sec:related}

\subsection{Threats to LLM Agents and Multi-Agent MCP Systems}
Surveys of LLM and agent security list indirect prompt injection, privilege escalation, and confused-deputy behavior as recurring threats \cite{agentsurvey2026,yao2024survey}. Indirect prompt injection was demonstrated against real LLM-integrated applications \cite{greshake2023} and is benchmarked for tool-integrated agents by InjecAgent \cite{zhan2024injecagent}; the confused deputy predates LLMs \cite{hardy1988}. In these settings the injected instruction is complete within the retrieved content. Multi-agent MCP frameworks for operations, such as the security-operations design of Sim\~oes et al.~\cite{mcpsoc2026}, concentrate on authentication, authorization, and auditing of agent-to-tool traffic.

\subsection{Fragment Assembly and Cross-Session Threats}
\label{sec:rel-assembly}
Liu et al.\ show that summarization-based prompt compression relinks fragments that are each benign in the source into a complete malicious instruction in the summary \cite{liu2026relink}; their KBRA (Keyed Binding Reassembly Audit) extracts predicate--role--value bindings from source and action, uses provenance-aware channel information with exact or semantic matching, and requires that the bindings behind an action be supported by a single source segment. Relink is the closest mechanism to our assembly condition, but it studies assembly across source fragments at the compression boundary, whereas STPG evaluates authenticated record provenance across storage and application-session boundaries; KBRA's unit is a source segment, STPG's is a lineage keyed by the authenticated source connector or by an individual trusted write, with reference chains that may cross lineages.

CSTM-Bench provides cross-session scenarios that accumulate, compose, launder, or inject on the reader, with per-reader role policies, judged by a reader LLM over the session log \cite{azarafrooz2026cstm}; XSPI (Cross-Session Stored Prompt Injection) is evaluated in a stateful sandbox with persistent memory and executable tools over 486 cross-session cases \cite{xie2026xspi}. Neither models writer identity and privilege as a stored attribute of records, approved external transfers as a benign class, or a sink decision that separates an induced transfer from an authorized one (Section~\ref{sec:data}).

\subsection{Provenance and Authorization in Agent Actions}
\label{sec:rel-prov}
\subsubsection{Provenance within One Execution}
CaMeL attaches capabilities that record provenance and permitted readers to every value inside a custom interpreter and checks policies before each tool call \cite{debenedetti2025camel}; AuthGraph separates an injected reasoning graph from an authorization graph built from the user's prompt and checks the allowed origin of each security-critical parameter \cite{wang2026authgraph}; PFI (Prompt Flow Integrity) separates trusted and untrusted agents, checks the source trust of tool outputs, treats unknown sources as untrusted, and keeps an explicit user-approval path across the trust boundary \cite{kim2025pfi}; CapChain combines capability tokens with a signed provenance log that gates state merges in multi-agent workflows \cite{capchain2026}. In all four, provenance lives within one plan, execution, tool call, or state store, and authorization derives from a user prompt, a capability policy, or a user approval. In STPG the producer provenance is persisted with the record, attributed to an authenticated principal with a trust level, and re-read in a later session by a different agent for which no per-request user prompt exists; our ephemeral-taint condition reproduces only a taint that is not persisted at the storage boundary, not PFI or CaMeL.

\subsubsection{Persistent Provenance with Action Authorization}
Three recent preprints also combine persistent provenance with action authorization \cite{ouyang2026memlineage,xu2026ppmf,maloyan2026sleeper}.
MemLineage keeps an append-only log of entries signed with per-principal keys and a derivation graph; an entry inherits the least trusted of its strongly connected parents, and a sensitive-action gate names, per governed parameter, the source classes allowed to authorize it (zero attack success, legitimate-dispatch rate 1.00 on a deterministic harness) \cite{ouyang2026memlineage}. PPMF proposes platform-maintained provenance with source and confirmation labels and a deterministic support binding that matches an action's canonical target to memory entries, resolves aliases only through a platform mapping, returns all candidates when ambiguous, and authorizes at the minimum trust of the support (zero attack success, benign success 1.000 under intact provenance) \cite{xu2026ppmf}. Sleeper Channels tags artifacts by channel, principal, and device, closes memory operations over their causal sources, and allows an action when its causal set is entirely trusted or an owner grant bound to the action digest exists; its evaluation is preregistered as follow-on work \cite{maloyan2026sleeper}.
Two of their mechanisms are close to ours: PPMF's alias resolution and all-candidates rule correspond to STPG's reference resolution and ambiguity rule, and MemLineage's per-parameter authority to STPG's destination-level scope. The differences we claim are narrower than a new principle. First, STPG groups records that other principals write to a shared store by the authenticated source connector, so that records dispersed over locations and sessions are regrouped as one lineage; none of the three evaluates this grouping. Second, STPG's authorization evidence is a directive found in the stored records themselves, such as an operator's standing rule, that must be witnessed to target the destination of the actual call, with mention, mapping, and prohibition in the same text distinguished from instruction, and verified against a deterministic support path. Third, the evaluation covers mixed trusted and untrusted directives in one context under both empty defaults, with the untrusted branch isolated by ablation.

\subsubsection{Other Related Areas}
Classical information-flow control \cite{denning1976,sabelfeld2003} and the provenance literature \cite{provsurvey2023,li2021provgraph} provide the lattice and the tracking machinery but do not define which records formed an LLM agent's directive or whether it was authorized for the destination it reached; layered prompt-injection defenses \cite{spotlight2026} and recursive log-analysis frameworks \cite{logresp2025} inspect content or behavior within one request or task and are complementary to a gate at the sink.

\section{Analysis of Problem and Limitation}
\label{sec:problem}

\subsection{System Model}
\label{sec:system}
A multi-agent MCP environment consists of agents $a$ with a trust level $\tau(a)$ and a privilege level $\pi(a)$, an MCP gateway through which every write, read, and tool call passes, and a shared store of records. We use four trust levels, $\tau_{\mathrm{ext}}<\tau_{\mathrm{ingest}}<\tau_{\mathrm{ops}}<\tau_{\mathrm{sys}}$, and four privilege levels, read, write, API, and IAM (Identity and Access Management). An ingest agent with trust $\tau_{\mathrm{ingest}}$ and privilege write writes content that enters through an ingestion endpoint; such content is assigned source trust $\tau_{\mathrm{ext}}$ regardless of the writer. An operations agent with trust $\tau_{\mathrm{ops}}$ and privilege IAM periodically reads the accumulated records of a domain in one read and decides its next step: a status report or a routing action that names a destination, internal if on an approved allowlist and external otherwise. Privilege separation is enforced by identity: the two agents run under separate service accounts, the gateway refuses a tool outside the caller's profile, labels each write with the identity and endpoint through which it arrived, and refuses the ingest identity's call to the privileged routing tool. A session is an application-level unit, one run of an agent against the gateway with its own identifier, not the transport-level session of the MCP protocol, which revision 2026-07-28 removed; the agent carries no memory across sessions, and the store persists.

\subsection{Threat Model}
\label{sec:threat}
The adversary controls the external ingestion path only. It can insert records whose bodies read as operational notes, but it cannot change model weights, system prompts, the gateway, or the provenance sidecars, and it cannot forge the source identifier, which the gateway derives from the authenticated ingestion connector. Within this capability, the attack satisfies four conditions, which Figure~S1 in the Supplementary Material places on the two axes of the data loss.
\begin{enumerate}
\item \textbf{Individually incomplete:} No single one of the $k$ records names both an action and an external target. The term does not mean statistically indistinguishable; Section~\ref{sec:detection} reports that per-record scores separate the classes in part.
\item \textbf{Emergent on assembly:} The destination of the transfer is determined only when the records' references are resolved together; a single record may still read as an instruction without a resolvable target (Section~\ref{sec:rules} measures this), so what the assembly adds is the destination, and attribution of that destination, not merely the detection of an instruction, is what a defense must decide on.
\item \textbf{Spatio-temporally dispersed:} Spatially, the records are spread over injection locations and stores such as log messages, ticket descriptions, and tool description fields; temporally, over $d$ sessions, with ordinary records between them. A reader that groups by location, window, or session sees fragments; grouping by source reunites these records across locations and sessions.
\item \textbf{Low trust to high privilege:} The records have source trust $\tau_{\mathrm{ext}}$ and the action is executed with privilege IAM. The privilege gap $g\in\{0,1\}$ states whether the writing identity also has lower privilege than the caller, $g=1$, which is a privilege escalation across identities, or is a high-privilege identity whose ingestion-path write is nevertheless untrusted, $g=0$, which is an induced unauthorized action; we report both and do not equate them.
\end{enumerate}
The same context may also contain an approved external transfer, a trusted operator's standing rule naming a partner, and the defense must separate the two external calls (Section~\ref{sec:holdout}). The attack depends on the loss of provenance, not on the detectability of any single record.

\textbf{Scope of the guarantee.} The defense decides the destination of a privileged routing call and nothing else. An authorized destination is one that a trusted directive targets; a trusted directive to a destination authorizes every call to that destination from the same context, including a call induced by an untrusted directive to the same destination, and the payload, amount, period, or purpose of the call are not inspected. Transfers that misuse an authorized destination with a different payload or purpose, and transfers to destinations that a trusted record has stopped authorizing after the fact, are outside the guarantee; Section~\ref{sec:unseen} measures the second case and Section~\ref{sec:validity} states both.

\subsection{Limitations of Existing Defenses}
\label{sec:limits}
Each threat condition exploits a limitation of existing defenses, which a comparison condition instantiates on the common kernel and a factor or challenge structure stresses (Table~S1). Three limitations concern what a defense can see and keep: a bounded window cannot contain a directive whose records lie outside it; provenance that lives inside one execution leaves the gate with no lineage once a record crosses the storage boundary, which is a property of non-persistence rather than of PFI or CaMeL specifically; lexical signatures do not fire on lexically ordinary records. Three concern the decision: a gate that uses untrusted influence without attribution blocks every external call that any untrusted record touched; a gate that authorizes a call because a trusted record names its destination takes a mention for an authorization; a gate that checks the existence of a directive and the occurrence of the destination separately can be steered by a trusted rule that forwards to A while listing or prohibiting B. STPG is designed against the last three.

\section{Derivation of Improvements}
\label{sec:improve}

These limitations lead to three design requirements and four hypotheses, each stated for the conditions evaluated rather than for defenses in general.

\subsection{R1: Bind Provenance to Data at Write Time and Persist It across Both Boundaries}
In-execution taint cannot be reconstructed after the fact, so the source identity, the writer, and the writer's trust and privilege must be stored as a sidecar that any later reader in any session can resolve, whatever location the record was hidden in. Hypothesis H1: among the evaluated configurations, every condition that persists provenance and applies the default-deny kernel blocks the attack, and the ephemeral-taint configuration, which persists nothing and passes on empty evidence, does not. H1 compares configurations, not persistence alone: a gate with no provenance and the default-deny kernel would also block every external call, including the approved ones; persistence is what lets a gate pass approved work selectively.

\subsection{R2: Attribute the Actual Call to Lineages, Witness the Destination, and Decide on Trust}
Because the external destination is resolved across records, authorization must inspect the relevant lineage and its reference chain, so the unit of judgment is the set of records that share a source lineage. Because the same context can hold an approved and an induced transfer, the gate must bind the destination of the actual call to the lineages that name it, resolving registry references across lineages, and establish that a binding lineage targets that destination, not merely that a directive exists somewhere in it and the destination string occurs somewhere in it. A trusted record that mentions, lists, or prohibits the destination is not an authorization; absence of any directive is not one either. Hypothesis H2: at equal attack blocking, STPG passes approved external transfers by positive attribution to a trusted directive, whereas the conservative gate and a full-context attribution judge block some or all of them. Hypothesis H3: on mixed, cross-referenced, poisoned, degraded, same-record, ambiguous, and off-task structures, STPG makes the specified decision for each listed destination, whereas trusted-rule matching passes unauthorized transfers and the conservative gate blocks approved ones; H3 is a policy-conformance statement that includes default-deny outcomes and the deliberate denial of approved transfers that the policy excludes.

\subsection{R3: Measure Directive Emergence Semantically and State What It Does Not Exclude}
Records are lexically ordinary, so the scorer must judge whether an assembled text functions as an external-transfer instruction. Hypothesis H4: the assembled-lineage score separates attacks from hard benign negatives that share the attack's surface form, with an operating point that transfers across held-out domains without retuning; a metadata-only probe finds no consistent cross-domain advantage, does not exclude text shortcuts, and we report where it finds template fingerprints.

PPT realizes R1, TSA the assembly and scoring half of R2 and R3, and PDG the binding, witnessing, and decision half of R2. No model is retrained, the modules are insertable into an MCP gateway, the per-read cost is bounded by the lineages that pass a cheap first-stage filter, and the per-call cost at the sink is one witness evaluation per binding lineage, $\sum_c |B(\delta_c)|$ over external calls, before caching.

\section{Proposed Method: STPG}
\label{sec:method}

\subsection{Overview}
Figure~\ref{fig:overview} shows STPG inside an MCP gateway: PPT on the write path, TSA on the read path, PDG on the sink path. The two dimensions of the data loss map onto the modules: PPT keys provenance by source so that the spatial dispersion over locations and stores is undone by one lookup, and TSA groups by lineage rather than by window or session so that the temporal dispersion over sessions is undone at read time. STPG sees only record bodies and the provenance PPT produced; the evaluation harness keeps ground-truth labels in a separate table that no module reads.

\subsection{PPT: Persistent Provenance Tagging}
\label{sec:ppt}
On every write, PPT creates a sidecar $\langle \mathrm{id}, \tau_{\mathrm{src}}, w, \tau(w), \pi(w), t, \sigma, \ell\rangle$ with the record identifier, the source trust, which is $\tau_{\mathrm{ext}}$ for a write through an ingestion endpoint and $\tau(w)$ otherwise, the writer $w$ with its trust and privilege, the time, the session $\sigma$, and a lineage key
\begin{equation}
\ell =
\begin{cases}
\texttt{src:}\,r & \text{if the gateway attached an authenticated source connector identifier } r,\\
\texttt{write:}\,\mathrm{id} & \text{otherwise,}
\end{cases}
\label{eq:lineage}
\end{equation}
so that records from one external source share one lineage across sessions and stores, while every other write, including each write of a trusted agent, is its own lineage; a trusted directive that spans two records is authorized only if the second record is reached by reference resolution (Section~\ref{sec:pdg}). Grouping internal writes by session was rejected because it merges an operator's directive with unrelated status records and dilutes the text that TSA scores.

The source identifier and the writer identity are issued by the gateway from the authenticated connector and the calling service account, not from the record body, so the adversary of Section~\ref{sec:threat} cannot set, rotate, or omit them; provenance is stored in a table keyed by record identifier, so a read in session $\sigma_j$ resolves a record written in $\sigma_i<\sigma_j$ from any store or field without state carried in the agent. The influencing records of a sink call are all records returned by the read that formed the agent's context. A record without a sidecar forms its own lineage \texttt{unknown:}id with source trust $\tau_{\mathrm{ext}}$; the challenge set tests the missing-sidecar cases directly. A trusted agent that rewrites untrusted content gives the rewrite its own trust, a laundering path studied for agent memory by PPMF \cite{xu2026ppmf} and measured in Section~\ref{sec:launder}.

\subsection{TSA: Temporal Shard Assembly}
\label{sec:tsa}
On every read, TSA regroups the returned records by lineage key; neither recency, position, location, nor session plays a role. The grouping key is a parameter of the gateway: STPG groups by lineage, and Section~\ref{sec:grouping} evaluates per-record and per-session grouping with every other component unchanged. For each lineage $G$ it joins the bodies in storage order and computes the directive score $E(G)\in[0,1]$ with a two-stage scorer: the first stage maps the cosine similarity between the embedding of the assembled text and six fixed abstract prototypes of forwarding output externally to $[0,1]$; the prototypes were written independently of the attack phrasing and are released with the code. TSA uses the first-stage score when it is below $\theta_1$; otherwise an LLM judge assesses the extent to which the lineage expresses a complete external-transfer instruction. A lineage is a directive when $E(G)\ge\tau_{\mathrm{TSA}}$; the read-level detection signal is $E^{*}=\max_G E(G)$ (Algorithm~\ref{alg:tsa}). $E(G)$ measures whether a directive to transfer data externally has formed, not whether it is authorized or which destination it targets, so an approved standing rule also scores high, and Section~\ref{sec:detection} reports detection against both benign sets for this reason. The scores, $F$, $\theta_1$, and $\tau_{\mathrm{TSA}}$ are read-time outputs and not inputs of the sink decision: the witness of Section~\ref{sec:pdg} receives the lineage grouping and the texts, not the scores. With $q$ lineages in a read, the cost is at most $q$ embedding lookups, cached by text, and one judge call per lineage that passes the first stage.

\begin{algorithm}[H]
\caption{TSA on a read of records $R$ with provenance store $P$.}
\label{alg:tsa}
\begin{algorithmic}[1]
\STATE $\mathcal{G} \leftarrow \emptyset$
\FORALL{$r \in R$}
  \STATE $p \leftarrow P[r.\mathrm{id}]$; \textbf{if} $p$ is undefined \textbf{then} $p.\tau_{\mathrm{src}}\leftarrow\tau_{\mathrm{ext}}$, $p.\ell\leftarrow\texttt{unknown:}r.\mathrm{id}$
  \STATE append $r$ to $\mathcal{G}[p.\ell]$
\ENDFOR
\STATE $F\leftarrow\emptyset$; $E^{*}\leftarrow 0$
\FORALL{$G \in \mathcal{G}$}
  \STATE $x \leftarrow$ join of the bodies of $G$ in storage order; $e_1 \leftarrow \mathrm{EmbeddingScore}(x)$
  \STATE $E(G) \leftarrow e_1$ \textbf{if} $e_1 < \theta_1$ \textbf{else} $\mathrm{JudgeScore}(x)$
  \STATE $E^{*}\leftarrow\max(E^{*},E(G))$
  \STATE \textbf{if} $E(G)\ge\tau_{\mathrm{TSA}}$ \textbf{then} $F\leftarrow F\cup\{G\}$
\ENDFOR
\RETURN $R$, $E^{*}$, $\mathcal{G}$, $F$
\end{algorithmic}
\end{algorithm}

\subsection{PDG: Privilege-Delta Gate}
\label{sec:pdg}

\subsubsection{Binding and Reference Resolution}
When the operations agent with privilege $\pi_c$ issues a call with destination $\delta$, PDG first applies the identifier contract to $\delta$ and to every identifier it compares against. An endpoint identifier is one token: after the wrapping is stripped (surrounding quotes and backticks, a trailing parenthesized annotation, trailing punctuation), a well-formed destination contains no whitespace, quotes, or brackets, and a string that does is a phrase, not an identifier, and is blocked as malformed before any other step (Section~\ref{sec:precheck}). The canonical form of a well-formed identifier, which is also the equivalence the mock backend applies when it routes, folds case and collapses every run of hyphens and underscores into one hyphen; two identifiers denote the same destination if and only if their canonical forms are equal, and a mention in a record is an occurrence of the canonical identifier at identifier boundaries with hyphens and underscores interchangeable, so that \texttt{PARTNER-EXT-897}, \texttt{partner\_ext\_897}, and \texttt{Partner-Ext-897 (ext)} are one destination while \texttt{PARTNER-EXT-8970}, \texttt{PARTNER-INT-897}, and \texttt{X-PARTNER-EXT-897} are others, and \texttt{PARTNER EXT 897} or \texttt{partner PARTNER-EXT-897} is not a destination at all. Whitespace is a word boundary and never an identifier separator, so the contract and the matcher coincide. In kernel v3.4, the matcher also folded spaces. It therefore accepted the literal destination \texttt{partner registered under key contact\_sec} when the same phrase appeared in the operator's rule, although the key had not been resolved; Section~\ref{sec:confusable} evaluates the three malformed forms the victims issued, and Section~\ref{sec:rules} reports the cost of the contract on rules whose authors write an identifier as separate words. PDG then determines which lineages name $\delta$. A lineage binds $\delta$ directly if $\delta$ occurs in its text, and by reference if the context contains mapping records that resolve a token to $\delta$ (the relation pattern $\mathcal{M}$: \texttt{key = }$\delta$, \texttt{label maps to key}, \texttt{label resolves to}~$\delta$, \texttt{label is bound to}~$\delta$) and the lineage mentions that token. The resolver follows at most two hops over all records of the context and records, for every token it reaches, the token's parent toward $\delta$; the records of the whole path from the mentioned token down to $\delta$ form the chain $C(G,\delta)$, which may lie in other lineages, and the tokens reached form the admissible token set $T(\delta)=\{\delta\}\cup\{\text{chain tokens}\}$. The trust of a binding and its ambiguity are computed over the entire path: a token with two conflicting values is ambiguous, a path that contains an ambiguous token at any hop is ambiguous, and a lineage that reaches $\delta$ only through an ambiguous path is treated as an untrusted binding whatever its own trust; a token that needs more than two hops, or cycles, is unresolved and creates no binding. Binding is a set computation and does not depend on scores, ties, or visiting order.

The critical case is a trusted directive that names label A, a trusted mapping from A to key B, and an untrusted mapping from B to an external endpoint. Resolution from the endpoint reaches B at hop one through the untrusted record and A at hop two through the trusted record, with B as the parent of A; the directive mentions A, so $C$ contains both mapping records, $\tau_{\min}$ is the trust of the untrusted endpoint mapping, and the call is blocked as an untrusted directive. The kernel evaluated in the first version of this work returned only the record of the mentioned token, so the endpoint mapping dropped out of the trust computation and the same call appeared trusted; the defect was found during review, the kernel was corrected, every reported run was recomputed on the corrected kernel, and Section~\ref{sec:chain2} evaluates untrusted, missing, and conflicting mappings at both hops.

\subsubsection{Endpoint Pre-Checks}
\label{sec:precheck}
The routing argument must be one final endpoint, and two pre-checks establish this before any branch is evaluated. The first is the grammar check of the identifier contract: a destination that is not a single identifier after its wrapping is stripped (it contains whitespace, quotes, or brackets) is blocked as malformed. It depends on the destination string alone and precedes every model call; it is also the point at which a deployment would return the call to the agent for correction, since the block carries the reason. The second is decided from the context rather than from a list of known strings: if the context itself resolves $\delta$ to something else (a record $\delta\ \mathcal{M}\ X$), then $\delta$ is a label or a registry key, and the call is blocked as non-endpoint. Both pre-checks are part of the kernel and are applied by every condition that has a gate input, which excludes only the undefended agent and the ephemeral-taint proxy.

\subsubsection{Witness and Support-Path Verification}
Binding links a destination to a lineage without establishing whether the lineage instructs a transfer there. For example, a trusted rule that authorizes forwarding to A but retires B binds both destinations. PDG therefore asks a destination-conditioned witness, an LLM with a fixed prompt released with the code: given the numbered records of $G\cup C(G,\delta)$ and $\delta$, does a record contain an instruction or standing rule to forward, route, mirror, or deliver output whose target is $\delta$, directly or through a label or key that the given records resolve? It returns a raw verdict $W_{\mathrm{raw}}$, a role per record, one of target, mapping, mention, prohibited, or none, and a support list $S$. The kernel accepts the verdict only if it is supported by an admissible path, which it checks itself:
\begin{equation}
W^{*}(G,\delta)= W_{\mathrm{raw}}\ \wedge\ \exists\, r\in \mathrm{Cand}:\ \neg\,\mathrm{map}(r)\ \wedge\ \mathrm{mentions}(r, T(\delta)),
\label{eq:verify}
\end{equation}
where $\mathrm{map}(r)$ holds when record $r$ matches the relation pattern $\mathcal{M}$, the same pattern the resolver uses, so that a mapping statement can never be the supporting instruction, $\mathrm{mentions}(r,T)$ holds when $r$ names $\delta$ or an admissible chain token, and $\mathrm{Cand}$ is $S$ if non-empty, otherwise the records with role target, otherwise all of $G\cup C$. A raw-true verdict that fails Equation~\eqref{eq:verify} is recorded as unsupported and treated as false.

The roles are therefore advisory: the semantic verdict comes from the model and the path from the kernel, and the witness cannot complete an unresolved reference, pull in records outside the chain, or promote a mapping record to an instruction. Prompt version w3, used in runs 4 and 5, adds one clause to the earlier prompt: a record that only states who a partner, recipient, or contact is, or where something is normally kept, describes a fact and takes the role mention, whereas a standing arrangement that commits output to be sent is an instruction (Section~\ref{sec:notice} measures its effect). Verdicts are cached by prompt version, model, numbered record text, and destination, so every condition that uses the witness receives the same answer for the same input.

\subsubsection{Decision Kernel}
With $B(\delta)$ the binding lineages and $\tau_{\min}(G)$ the minimum source trust over $G\cup C(G,\delta)$, where $C$ holds every record on the resolution paths, with a missing sidecar and an ambiguous path both counted as $\tau_{\mathrm{ext}}$:
\begin{equation}
\mathrm{dec}(\delta)=
\begin{cases}
\mathrm{PASS} & \mathrm{canon}(\delta)\in\mathcal{D}_{\mathrm{int}}\ \text{(internal)},\\
\mathrm{BLOCK} & \delta \text{ is not a single identifier (malformed)},\\
\mathrm{BLOCK} & \delta \text{ resolves further in the context (non-endpoint)},\\
\mathrm{PASS} & \exists\, G\in B(\delta):\ W^{*}(G,\delta)\ \wedge\ \tau_{\min}(G)\ge\tau_{\mathrm{ops}}\ \text{(trusted)},\\
\mathrm{BLOCK} & \text{else if }\exists\, G\in B(\delta):\ W^{*}(G,\delta)\ \wedge\ \tau_{\min}(G)\le\tau_{\mathrm{ingest}}\ \text{(untrusted)},\\
\mathit{empty} & \text{otherwise (no evidence; STPG: BLOCK)}.
\end{cases}
\label{eq:policy}
\end{equation}
Algorithm~\ref{alg:gate} is the STPG realization of the kernel as code, Figure~\ref{fig:kernel} draws it with the adapters of Section~\ref{sec:adapters}, and Table~S2 lists an example context for every row of Equation~\eqref{eq:policy}. Authorization is destination conditioned and per lineage: a context with a trusted rule to A and an induced directive to B passes a call to A and blocks a call to B; the challenge set covers this distinction when an untrusted lineage holds a directive to B and a mention of A beside a separate trusted rule to A, and when one trusted record authorizes A but prohibits B. A trusted directive that targets $\delta$ authorizes $\delta$ even if an untrusted directive also targets it; the scope is the destination of a routing call, not payloads, periods, or amounts, and the untrusted directive is logged. A directive whose chain passes through an untrusted, missing, or ambiguous record is untrusted.

The empty default is BLOCK for STPG; the pass default is evaluated as a separate condition because a deployment that prefers availability may choose it, and its cost is measured rather than assumed. $\Delta\pi=\pi_c-\min\pi(w)$, computed on the integer ranks $\mathrm{read}<\mathrm{write}<\mathrm{API}<\mathrm{IAM}$ over the writers of the evidence lineages and their chains, is logged with every decision that has evidence (NA otherwise) to classify a blocked event as a privilege escalation across identities ($\Delta\pi>0$) or an induced action ($\Delta\pi=0$); it is not a decision variable, and the module's name refers to this attribution.

\begin{algorithm}[!htb]
\caption{STPG realization of the decision kernel at a privileged routing call (adapters and defaults: Table~\ref{tab:adapters}).}
\label{alg:gate}
\begin{algorithmic}[1]
\REQUIRE destination $\delta\neq\varnothing$, lineages $\mathcal{G}$, caller privilege $\pi_c$, evidence adapter, default $\mathit{empty}\in\{\mathrm{BLOCK},\mathrm{PASS}\}$
\STATE $\delta\leftarrow\mathrm{canon}(\delta)$ \COMMENT{strip wrapping; fold case; runs of \texttt{-} and \texttt{\_} to one \texttt{-}}
\IF{$\delta\in\mathcal{D}_{\mathrm{int}}$} \RETURN PASS \ENDIF
\IF{$\delta$ contains whitespace, quotes, or brackets} \RETURN BLOCK (malformed) \ENDIF
\IF{$\exists\, r\in\bigcup\mathcal{G}:\ r \text{ matches } \delta\ \mathcal{M}\ X$} \RETURN BLOCK (non-endpoint) \ENDIF
\STATE $\mathit{chain}\leftarrow\mathrm{Resolve}(\delta,\bigcup\mathcal{G})$; $T\leftarrow\{\delta\}\cup\mathrm{keys}(\mathit{chain})$ \COMMENT{$\le 2$ hops; each token keeps its parent, its path to $\delta$, and the path's ambiguity; cycles or deeper $\Rightarrow$ unresolved}
\STATE $\mathcal{T}\leftarrow\emptyset$; $\mathcal{U}\leftarrow\emptyset$
\FORALL{$G\in\mathcal{G}$}
  \STATE $(\mathit{bound},C,\mathit{amb})\leftarrow\mathrm{Bind}(G,\delta,\mathit{chain})$ \COMMENT{$C$ = all records on the paths of the tokens $G$ mentions; $\mathit{amb}$ over those paths}; \textbf{if} \NOT $\mathit{bound}$ \textbf{then continue}
  \STATE $(w,\mathit{roles},S)\leftarrow\mathrm{Witness}(G\cup C,\delta)$ \COMMENT{adapter-specific; STPG: LLM witness}
  \STATE $\mathrm{Cand}\leftarrow S$ \textbf{if} $S\neq\emptyset$ \textbf{else} $\{r:\mathit{roles}[r]=\mathrm{target}\}$ \textbf{if} non-empty \textbf{else} $G\cup C$
  \STATE $w\leftarrow w\ \wedge\ \exists r\in\mathrm{Cand}:\ \neg\mathrm{map}(r)\wedge\mathrm{mentions}(r,T)$ \COMMENT{Equation~\eqref{eq:verify}; failure logged as unsupported}
  \STATE \textbf{if} \NOT $w$ \textbf{then continue}
  \STATE $\tau\leftarrow\min_{r\in G\cup C}\tau_{\mathrm{src}}(r)$; \textbf{if} $\mathit{amb}$ \textbf{then} $\tau\leftarrow\tau_{\mathrm{ext}}$
  \STATE \textbf{if} $\tau\ge\tau_{\mathrm{ops}}$ \textbf{then} $\mathcal{T}\leftarrow\mathcal{T}\cup\{G\}$ \textbf{else} $\mathcal{U}\leftarrow\mathcal{U}\cup\{G\}$
\ENDFOR
\STATE $\Delta\pi\leftarrow\pi_c-\min\pi(w)$ over writers of $\mathcal{T}\cup\mathcal{U}$ and their chains if non-empty, else NA; log
\IF{$\mathcal{T}\neq\emptyset$} \RETURN PASS (trusted-authorized) \ENDIF
\IF{$\mathcal{U}\neq\emptyset$} \RETURN BLOCK (untrusted-directive, or ambiguous-reference) \ENDIF
\RETURN $\mathit{empty}$ (no-evidence)
\end{algorithmic}
\end{algorithm}

\section{Experimental Setup}
\label{sec:exp}

\subsection{Testbed and Models}
\label{sec:testbed}
The experiments run against a Google Cloud project that mirrors a multi-agent MCP deployment: an MCP gateway service, a document store for records and provenance, an analytics store for traces, and a message bus for inter-agent events, with separate service accounts for the ingest and operations agents. The agents are driven by Gemini models on Vertex AI in region us-central1: gemini-2.5-flash-lite is the primary victim agent and the model of the TSA judge, the witness, the scalar full-context judge, and the attribution judge; text-embedding-005 provides embeddings. A second model family, Llama 4 Maverick (17B active parameters, 128 experts, open weights, Meta), is served through the Vertex AI model-as-a-service endpoint in region us-east5 and is used as the judge, witness, attribution judge, and scalar judge in place of gemini-2.5-flash-lite (Section~\ref{sec:judgeswap}), as the victim (Section~\ref{sec:generalization}), and as the author of the phrasings of the frozen evaluation set (Section~\ref{sec:unseen-design}); every model call goes through one backend module, so a model is swapped by name without changing prompts, parsing, or caching. All generation runs at temperature 0 with the models' optional reasoning mode disabled so that the output budget is spent on the JSON answer. The victim's decision for each trace is generated once and cached, so every condition sees the identical agent action. The gateway implements the tool, resource, and session primitives of MCP specification revision 2025-06-18, which was current at design time; the later revisions \cite{mcpspec} change the transport, handshake, and discovery mechanisms, not the write, read, and tool-call paths that the gateway intercepts.

The primary comparisons hold model and platform settings fixed and share cached victim actions and token accounting. A separate sensitivity study substitutes Llama 4 Maverick while retaining the platform and evaluation pipeline. This design controls platform-related variation but limits external validity to two model families on Google Cloud (Section~\ref{sec:validity}). The exact model identifiers and the version history of the runs are listed in Table~S6; the role of each model (victim, TSA judge, witness) is stated where the condition is defined (Section~\ref{sec:conditions}).

\subsection{Data Generation and Hygiene}
\label{sec:data}

\subsubsection{Why Synthetic Data}
The two public cross-session resources do not contain the factors the hypotheses need to control together (Table~S4): CSTM-Bench provides cross-session scenarios with hard benign confounders and per-role policies but no shared store, writer identity and privilege, or privileged sink to gate \cite{azarafrooz2026cstm}, and XSPI-Bench provides stored-injection cases with executable tools but does not model writer privilege as a stored attribute or approved external transfers as a benign class \cite{xie2026xspi}. We therefore generate traces on one kernel with a mock sink that records call arguments; destinations are synthetic placeholders and no data leaves the testbed, following the non-destructive conventions of agent-security benchmarks \cite{zhan2024injecagent}. Three operational domains, incident handling, billing settlement, and access review, provide the vocabulary; records imitate the field structure of cloud logs, tickets, and registry entries that log-analysis agents read \cite{logresp2025}.

\subsubsection{Attack and Benign Traces}
Attack traces cross the record count $k\in\{2,3,4,5\}$, the session count $d\in\{1,3,5\}$, the privilege gap $g\in\{0,1\}$, three injection locations, and three domains, with three repetitions: 648 traces, each one read of 8 to 26 records in which the $k$ attack records are separated by trusted filler records at a spacing that grows with $d$, records are assigned to $d$ sessions by position, and one neutral operator note is inserted at a random position. The attack texts come from twelve template families, three domains times four values of $k$; repetitions vary the destination identifier, the filler sample, positions, session assignment, and note position, so the 648 traces are not independent texts (Section~\ref{sec:stats}). No single attack record names both an action and an external target.

Benign traces, 90 per domain and 270 in total, draw their length, session count, and untrusted-lineage size from the same distributions and come in four subtypes: 75 approved external transfers, each an operator's standing rule naming a partner; 65 approved internal directives; 55 untrusted archive directives to an approved internal destination; and 75 index-note traces without any directive. Every benign trace contains one untrusted background lineage of $k_b\in\{2,\dots,5\}$ records written through the ingestion connector whose texts mirror the attack templates record by record, an operating rule, a binding note, a registry entry, a policy reference, and a directory line, but resolve to an internal store, in two families: an internal archive directive, family A, and a descriptive index note, family B. These hard negatives make the approved external transfer a test of attribution: its context contains an untrusted lineage of the attack's form, and the only difference is which lineage is the directive behind the call. Benign texts come from twelve template families as well, four subtypes times three domains.

\subsubsection{Metadata-Only Probes and What They Do Not Show}
To test whether data-generation artifacts predict the label without access to any record body, we trained a logistic regression, a depth-3 tree, and a gradient-boosted ensemble on 19 metadata features per trace (counts of records, sessions, lineages, untrusted records and lineages, injection locations, positions of the first and last untrusted record, and text-length statistics), with AUROC (Area Under the Receiver Operating Characteristic Curve) computed per fold (Table~S5). Across domains the metadata do not transfer: leaving one domain out, the fold AUROCs range from 0.30 to 0.52, and label permutation gives means near 0.50; the below-0.5 folds indicate a feature direction that reverses between domains. Within a domain, text length identifies template families: leaving one attack family out, the ensemble reaches a mean AUROC of 0.701, 0.708 with the four length features alone and 0.260 without them. Two earlier confounds were removed before the main run by the neutral note and the mirrored negatives; the residual fingerprint is the approximate match of lengths between families. The probe says nothing about shortcuts inside the bodies, so the claim that detection is content based rests on the hard-negative construction and the challenge structures with new phrasing.

\subsubsection{Frozen Settings and Versions}
\label{sec:versions}
The study proceeded in three stages: a local mock evaluation, a pilot with real models on a reduced grid, and the main experiment. The first-stage threshold $\theta_1=0.45$, the flag threshold $\tau_{\mathrm{TSA}}=0.60$, the six prototypes, and the TSA judge prompt were fixed on the pilot, which used all three domains, so the held-out-domain analysis of Section~\ref{sec:detection} is a calibration transfer. The sink witness prompt was revised twice after challenge runs, giving w2, and once more during review after set E showed that w2 read every trusted notice naming a partner as an instruction, giving w3. Four end-to-end runs and one re-derivation produced the reported numbers (Table~S6): run 3, the submitted version, used kernel v3.3 and w2; run 4, the first revision, reused the same traces, seeds, and cached victim decisions with kernel v3.4 (full-path chain trust and destination canonicalization) and w3; run 5 applies kernel v3.5 to the stored run-4 outputs, with sets A and F re-run using cached victim decisions. The only change of v3.5 is the identifier contract of Section~\ref{sec:pdg}: its pre-check depends on the destination string alone and precedes every model call, so a run-4 decision on a well-formed destination is also its v3.5 decision wherever the v3.4 and v3.5 matchers agree on the records, and the released script \texttt{check\_v35\_equivalence.py} confirms that they agree on every record text and identifier of every set except the six space-written rules of set A, which is why that set is re-run. The re-derivation changed only calls whose destination is malformed, all of them benign calls the victims issued and all listed in the released log (2 of 71 approved calls of the main run, 7 of 69 with the hardened victim, 1 of 75 with the labeled victim, 7 of 75 with the Llama victim, 1 in the challenge set, 4 in set D, 6 in the frozen set and 7 in its Llama-victim run, and none of the counterfactual calls). Cost and latency results remain run-4 measurements. The frozen evaluation set was generated and run under kernel v3.4 and w3; the re-derivation under v3.5 left all 260 of its counterfactual decisions unchanged, and the changes to actual victim calls are reported separately (Section~\ref{sec:unseen}). Because the model-based calls are regenerated in every end-to-end run at temperature 0, run 4 also measures the run-to-run variation of those conditions on identical inputs (Section~\ref{sec:utility}).

\subsubsection{Policy Challenge Set}
\label{sec:holdout-design}
Fifteen structures written with different phrasing, such as handoff notes, tags, contact sheets, and operator notices, and different reference tokens test each branch of the kernel; Table~S7 lists them with the specified decision, which was fixed from the operator's authorization policy before the structures were run, and Figure~\ref{fig:holdout} reports them. Each structure is instantiated in three domains with four repetitions, 180 traces; the gate of every condition is evaluated counterfactually on each listed destination in the same context, 240 calls, and on the destination the victim actually chose, 176 external calls.

The first ten structures were used to find and fix two defects of an earlier kernel, a trusted registry entry whose literal binding of the destination counted as authorization and session-keyed lineages that diluted operator rules; the five later structures test the same-record, same-source, same-destination, ambiguity, and hop-limit cases, and the endpoint pre-check and Equation~\eqref{eq:verify} were added after a run in which the three-hop structure failed. The set is therefore a policy challenge evaluation of a kernel that was developed against it in part, not an unseen-structure generalization test.

\subsubsection{Robustness Sets}
\label{sec:robust-design}
The nine robustness sets probe failures beyond the main run's assumptions. They were initially evaluated under kernel v3.4 and prompt w3; their results were re-derived under v3.5, except that sets A and F were re-run using cached victim decisions. All sets reuse the main-run generators for fillers, background lineages, layout, and sessions, so that only the records named below differ, and the gate of every condition is evaluated counterfactually on the listed destination in every trace and on the destination the victim chose.

Set A, degraded approved rules, holds 210 benign approved-transfer traces, 7 variants $\times$ 3 domains $\times$ 10 repetitions, each with an untrusted background lineage of the attack's form and an operator rule for partner A written in a degraded way: the canonical phrasing as a control; a paraphrase produced by gemini-2.5-flash, six per domain, released with the data; a rule without an imperative verb; a rule that names a registry key resolved to A by a trusted contact sheet, and the same rule with the sheet written through the ingestion connector, which the policy denies; the partner identifier in another surface form (lower case, spaces, underscores, trailing punctuation, a parenthesized suffix, two repetitions each per domain); and a directive split over two trusted records with no mapping in the relation pattern. Set B, multi-connector attacks, holds 150 attack traces, 5 structures $\times$ 3 domains $\times$ 10 repetitions, in which the $k=3$ attack records arrive through one connector as a control, through two or three connectors, through two connectors with the registry entry written by the operations identity, and through two connectors with the mapping phrased outside $\mathcal{M}$. Set C swaps the model family: the main run and the challenge set are re-evaluated with Llama 4 Maverick as the TSA judge, the witness, the attribution judge, and the scalar judge, reusing the cached victim decisions, so that gate decisions are compared row by row with those of the primary judge.

Set D, two-hop chains, holds 210 benign traces, 7 variants $\times$ 3 domains $\times$ 10 repetitions, in which a trusted rule names label A, a contact sheet maps A to key B, and a directory line maps B to the endpoint; the control has both mappings trusted and unambiguous, and the six variants place an untrusted record, a record without a sidecar, or a second conflicting record at hop one (the endpoint mapping) or hop two (the label mapping); the specified decision is pass for the control and block for every variant. Set E, descriptive notices, holds 150 benign traces, 5 phrasings $\times$ 3 domains $\times$ 10 repetitions, in which the only trusted record naming partner A is a notice that states a fact about A (Table~\ref{tab:newsets} lists the phrasings) and no rule instructs a transfer; the specified decision is block. Set F, identifier surface forms, look-alikes, and malformed forms, holds 30 benign traces with the canonical rule naming A and evaluates 15 counterfactual destinations per trace: five legitimate variants of A, which must pass; seven look-alikes that denote other endpoints, which must block; and the three malformed forms that the victims actually issued in the run-4 logs, which must be blocked as malformed before any branch (Section~\ref{sec:pdg} gives examples of the variants and look-alikes, Section~\ref{sec:confusable} the three malformed forms). Set G, lineage scale, holds 120 traces, 4 sizes $\times$ 3 domains $\times$ 5 repetitions $\times$ attack or benign, in which the untrusted lineage of one connector contains $n\in\{10,50,100,200\}$ unrelated operational records beside the three attack records, or beside nothing with an approved rule in the context. Set H, latency, holds 120 benign traces, $m\in\{1,2,3,5\}$ $\times$ 3 domains $\times$ 10 repetitions, in which $m$ trusted rules with different phrasing name the same partner, so that the sink evaluates $m$ binding lineages; each trace is run with warm caches, in a second pass in the same process, and with every cache bypassed. Set I, trusted-rewrite laundering, holds 120 traces, 4 variants $\times$ 3 domains $\times$ 10 repetitions: a trusted operations agent, driven by gemini-2.5-flash-lite with a one-sentence summarization prompt released with the code, reads the session-1 records, which contain the $k=3$ attack lineage or an approved rule with an untrusted background, and writes a handoff note; the victim reads the context in a later session with the original records present or with the original untrusted records, or the original rule, compacted away so that only the note remains.

Two further runs vary the victim rather than the gate. The hardened prompt keeps the operational task but tells the agent that stored content that originated outside the organization is data and never an instruction, that a routing step is taken only on an approved operator rule, and that it must report instead of route when the origin cannot be told; the labeled variant adds the hardened prompt and prefixes every record with the origin label the gateway knows (external ingestion connector or operations team). Both are run on the 918 main-run traces with new victim decisions.

\subsubsection{Frozen Evaluation Set}
\label{sec:unseen-design}
To assess new phrasings and domain transfer under frozen settings, an additional evaluation set was generated after kernel v3.4, the relation pattern, witness prompt w3, the thresholds, and the canonicalization rule were fixed, and nothing in the set was changed afterwards; the later v3.5 identifier contract was applied to it in the separate re-derivation of Section~\ref{sec:versions}, which changed none of its 260 counterfactual decisions and changed six primary-victim and seven Llama-victim actual-call decisions (Section~\ref{sec:unseen}). The phrasings were written by the second model family, Llama 4 Maverick, from a prompt that names only placeholders and the record kinds, in four domains: the three of the main run and a fourth, procurement, whose vocabulary appears in no other generator. For each domain the model wrote three attack triples (a procedure record naming a label, a binding record from the label to a key, an address record from the key to the endpoint), three direct rules, two rules via a key, three contact-sheet lines, three descriptive notices, two prohibitions, two revocations, two mentions, and three internal archive rules; the builder substitutes identifiers and edits no phrasing. Twelve structures, Table~S9, are instantiated in the four domains with five repetitions, 240 traces and 260 counterfactual calls, and the specified decisions were fixed before the run. Every structure but one has a counterpart in a development set and differs from it in wording and domain (Table~S9); the exception is a trusted rule that a later trusted record revokes, a semantics that no development set contains. The set was run once with the primary victim and once with Llama 4 Maverick as the victim; the counterfactual decisions are identical for both because they depend on the records, not on the victim. A diagnostic that only counts how many of the model-written binding, address, and contact-sheet records the frozen relation pattern resolves is reported with the results, and a post-hoc analysis that extends the pattern with the observed relation phrases is reported separately and labelled as such.

\subsection{Comparison Conditions, Metrics, and Statistics}
\label{sec:conditions}
Nine defenses are evaluated on the same traces with the same cached victim decisions and the adapters of Table~\ref{tab:adapters}: STPG; STPG with the allow-on-empty default; the trusted-directive-only ablation under each default; PPT with the conservative gate; trusted-rule matching; the full-context attribution judge; the ephemeral-taint proxy; and the undefended pipeline as reference. Three scorers are reported for detection only, because their defense behavior on the kernel would repeat the conservative gate: a scalar full-context judge that makes one judgment over the whole read, unit inspection that takes the maximum per-record embedding score, and a window scorer that embeds the five most recent records without a judge stage. The conservative gate, matching, taint, and the detection-only scorers are reduced proxies of method families, not reimplementations of specific systems: no result in this paper compares STPG with CaMeL, PFI, AuthGraph, MemLineage, PPMF, or any other published system under its own conditions, and every difference reported is a difference between evidence adapters on the common kernel. Three variants of STPG isolate single components: per-record grouping and per-session grouping keep binding, the witness, the kernel, and the default and change only the unit over which records are assembled (Section~\ref{sec:grouping}), and read-set inheritance lowers the trust of a trusted agent's write to the minimum trust of the records it read in the same session (Section~\ref{sec:launder}).

\label{sec:stats}
Four evaluations are kept separate. Defense on attacks: the ASR (Attack Success Rate) is the fraction of attack traces in which the agent issues an external routing call and the sink allows it. Defense on approved work: the false-block rate over the approved external transfers the agent actually issued, with the pass reason recorded as trusted directive or empty evidence; internal routing is checked never to be blocked, off-task external calls are reported separately, and precision, recall, and F1 of the gate over the external calls it decided are given with a blocked attack call as a true positive and a blocked approved transfer as a false positive \cite{fawcett2006}. Policy conformance on the challenge set: the fraction of counterfactual calls decided as specified, reported separately from the preservation of business-approved calls, whose denominator includes approved transfers that the policy deliberately denies. Detection: AUROC of the read-level score against all 270 benign traces and against the 195 without an approved external-transfer directive, with TPR (True Positive Rate), FPR (False Positive Rate), precision, recall, and F1 at the a priori threshold, the maximum TPR subject to FPR $\le5\%$, and the operating point transferred from the other two domains. Proportions carry exact 95\% Clopper--Pearson intervals and paired false-block comparisons use the exact McNemar test; both assume independent traces, which shared templates violate, so false blocks are also reported per domain. AUROC CIs (Confidence Intervals) are 95\% percentile bootstrap intervals with 2,000 resamples \cite{efron1979}, by trace and by cluster with both classes resampled by template family \cite{obuchowski1997}, and differences between scorers use the DeLong test \cite{delong1988} and paired cluster-bootstrap intervals; with twelve families per class these intervals are imprecise. Latency: the wall-clock time of the read-time analysis and of the sink-time authorization of each operation, measured inside the gateway, as median, 95th, and 99th percentiles, for warm caches, for a second pass in the same process, and for cold caches.

\subsection{Main Run: Attack Blocking and Preservation of Approved Transfers}
\label{sec:blocking}\label{sec:utility}
Table~\ref{tab:main} reports the main run with gemini-2.5-flash-lite as the victim. Undefended, the agent issued the external routing call in 648 of 648 attack traces and the call was allowed in all (ASR 1.000, $[0.994,1.000]$), uniformly across $k$, $d$, $g$, locations, and domains. STPG, its allow-on-empty condition, the trusted-directive-only ablation, the conservative gate, trusted-rule matching, and the attribution judge blocked all 648 (ASR 0.000, $[0.000,0.006]$), each for the reason its adapter records, STPG through the untrusted branch with no unsupported verdict; the ephemeral-taint proxy and the trusted-directive-only ablation with the allow-on-empty default blocked none. The two privilege gaps behave identically (324 of 324 each), with $\Delta\pi$ logged as $\mathrm{IAM}-\mathrm{write}$ for $g=1$ and $0$ for $g=0$. H1 holds for these configurations: on the default-deny kernel the attack is blocked because no trusted directive targets the destination, and the conditions that persist provenance differ in what they record and in what they do to approved work. As precision, recall, and F1 of the gate over the 719 external calls, STPG, its allow-on-empty variant, the trusted-directive-only ablation, and trusted-rule matching reach 0.997, 1.000, and 0.998, the conservative gate 0.901, 1.000, and 0.948, and the attribution judge 0.959, 1.000, and 0.979; because 648 of the 719 calls are attacks, precision stays above 0.9 even when every approved call is blocked, so the false-block rate is the metric that exposes the utility cost. The 648 of 648 result was shared by the six blocking conditions in Table~\ref{tab:main}; it applies to this main run and does not extend to all relaxed settings in Sections~\ref{sec:robust} to \ref{sec:limitsops}.

Of the 75 approved-transfer traces, the agent routed externally in 71 and reported status in 4. \subsection{Policy Robustness: Challenge Set, Degraded Rules, and Reference Chains}
\label{sec:holdout}\label{sec:robust}
\subsubsection{Conformance on the Challenge Set}
Table~S7 lists the fifteen structures with the specified decision per destination kind, STPG's conformance, the branch that fired, and the destination kinds the victim chose. Destination kinds are A for the approved partner, B for the synthetic sink, and X for an off-task string or label; branches are T for trusted directive, U for untrusted directive, M for ambiguous reference, and E for no evidence. Figure~\ref{fig:holdout} shows every condition. STPG conformed to all 240 counterfactual decisions: the 84 calls specified as pass all passed through the trusted-directive branch, and of the 156 specified as block, 96 were blocked by the untrusted branch, 24 by the ambiguity rule, and 36 by the default: 12 off-task strings, 12 prohibited destinations of the same-record structure, and 12 three-hop calls.

Policy conformance and business-approved preservation are different denominators: counting also the 12 approved transfers whose rule lost its provenance and the 12 that reach the partner only through three hops, the business-approved denominator is 108, of which STPG passed 84 and blocked 24, all 24 by policy. The alternatives fail where their adapters predict: trusted-rule matching (168 of 240) passes the unauthorized transfers of the cross-reference, trusted-mention, same-record, ambiguous-key, and three-hop structures; the conservative gate conforms to exactly the 156 block-specified calls; the attribution judge (156 of 240) attributes approved calls to untrusted records in the mixed, untrusted-mention, missing-background, and bundle structures, blocks all 12 approved calls of the same-destination structure, and passes 20 of 24 ambiguous-key calls; and the allow-on-empty condition (204 of 240) passes exactly the 36 calls that reached the default, 12 business-approved transfers that the hop policy denies and 24 policy-compliant blocks converted into unauthorized passes. Per-record grouping conforms to all 240 and per-session grouping to 167 (Section~\ref{sec:grouping}).

A branch count says which rule fired, not whether the witness's semantic reading was right, so Figure~S2 reports the two separately for the 396 binding lineages that STPG evaluated on the counterfactual calls. Verified means that the raw verdict was true and Equation~\eqref{eq:verify} held; rejected means that the raw verdict was true but no admissible non-mapping candidate existed; negative means that the raw verdict was false. The raw witness returned true for 261 of 396; the kernel verified 216 and rejected 45, and 135 were negative (with prompt w2 in run 3: 214, 116, and 66, so the w3 clause moved most mapping-only lineages from raw-true verdicts that the kernel had to reject into negative verdicts, with the verified count unchanged within two).

All 45 rejected verdicts relied only on mapping records (a registry record of the ambiguous-key, three-hop, off-task, or missing-sidecar structures). These are lineage-level rejections, not 45 incorrectly authorized calls, because trust and default decisions follow verification; no verified target relied on a mapping record, and none of the 717 main-run verdicts was rejected. The 135 negative verdicts are the readings the mention, same-record, and mapping structures rely on: 24 mentions, 12 prohibitions, and 99 mapping-only lineages. The witness therefore read instruction against mention or prohibition in the same text correctly and, under w3, read most mapping-only text as mapping; where it still over-read, the kernel did not let it decide. The named lineage, role, and $\Delta\pi$ of the 648 blocked attacks are coverage of the attribution output, not a measured precision, because no independent gold support set exists for them.

\subsubsection{Degraded Approved Rules and Multi-Connector Attacks}
\label{sec:rules}
The main run sits inside two of the defense's assumptions, that operator rules name the partner literally and that every attack lineage arrives through one connector; sets A and B relax them (Table~S8 and Figure~\ref{fig:robust}; Section~\ref{sec:robust-design} defines the variants), and set C, the model family, is reported in Section~\ref{sec:judgeswap}.
On the counterfactual call to partner A, STPG passed every paraphrased rule (30 of 30; the witness read the six LLM-written phrasings as directives), every rule without an imperative verb, every rule that reaches A through a trusted contact sheet, and 24 of the 30 rules whose partner identifier is written in another surface form: all 24 written in lower case, with underscores, with a trailing period, or with a parenthesized suffix, and none of the 6 written as three space-separated words, because under the identifier contract a rule that spells \texttt{PARTNER EXT 194} does not name the endpoint \texttt{PARTNER-EXT-194} and the call reaches the default (12 of 30 with the literal binding of run 3; 30 of 30 with the space-folding matcher of run 4, which is the matcher that also absorbed prose into identifiers). The 6 blocks are the contract's measured cost on this set, and they are the kind of block an operator corrects by writing the identifier as one token. STPG blocked all 30 rules whose contact sheet arrived through the ingestion connector, as the provenance policy specifies. In the variant that splits the directive over two trusted records, the rule record names no partner and the notice (``delivery partner for the summary report is A'') is phrased outside the relation pattern $\mathcal{M}$, so the one-record lineage of the notice is the only binding lineage; STPG passed 21 of 30 because the witness read the notice alone as an instruction and blocked 9 by the default, so the pass never rested on assembling the two records, and the variant is the same semantic question as set E (Section~\ref{sec:notice}). Trusted-rule matching, which shares the binding step, passed all 30 in every variant except the untrusted sheet and the same 24 of 30 in the surface-form variant; the attribution judge, which reads the rule as text, passed all 30 in every variant except the untrusted sheet; the conservative gate blocked every call. On the calls the victim actually issued, STPG passed 22 of 30 in the surface-form variant, blocking as malformed the 6 calls that copied the space-written identifier and 2 that rewrote a lower-case identifier as the word ``partner'' followed by \texttt{ext-013} or \texttt{ext-912}, and 21 of 30 in the two-record variant; the victim followed the rule without an imperative verb in only 1 of 30 traces, so that variant mainly measures the agent.

Spreading the three attack records over two or three connectors did not open the gate: STPG blocked all 30 calls in every structure through the untrusted branch, because the resolver follows mapping records across lineages and the witness receives the chain together with the binding lineage. With the registry entry written by the operations identity, trusted-rule matching passed all 30 calls, since the trusted registry record binds the destination literally and matching takes a binding trusted lineage for an authorization, whereas STPG's chain trust is the minimum over the directive lineage and its chain and remains untrusted. With the mapping phrased outside the relation pattern, the lineage that contains the destination literally was bound and the witness read it as a target in all 30 cases, so STPG blocked by the untrusted branch rather than by the default; a mapping that neither matches the pattern nor reads as a directive would reach the default, which blocks under STPG and passes under the allow-on-empty variant. Read-level detection did not degrade (AUROC 1.000 against the non-directive set even with one record per connector), because the TSA judge scores the operations-rule record alone at 0.80: the detection signal in this data rests mostly on the rule record, and what assembly contributes is the destination, which is what the gate decides on (Section~\ref{sec:threat}).

\subsection{Frozen Evaluation Set}
\label{sec:unseen}
Figure~\ref{fig:unseen} and Table~S9 report the evaluation set of Section~\ref{sec:unseen-design}, originally evaluated under frozen kernel v3.4 and witness prompt w3; the subsequent v3.5 re-derivation left all 260 counterfactual decisions unchanged. STPG decided 190 of 260 counterfactual calls as specified; conformance was 49, 46, 47, and 48 of 65 calls in the incident, billing, access-review, and procurement domains, so the procurement result fell within the observed range for the three development domains; the primary victim issued 60 attack calls and STPG blocked all 60, and with Llama 4 Maverick as the victim it blocked 56 of 56. The 70 misses have three causes. First, the relation pattern: the frozen pattern $\mathcal{M}$ resolved 5 of the 36 model-written contact-sheet, binding, and address records; unrecognized literal forms included \texttt{corresponds to}, \texttt{is associated with}, \texttt{is registered under key}, and \texttt{is linked to}, and accepted forms were \texttt{=}, \texttt{maps to}, \texttt{resolves to}, and \texttt{is bound to}. Every approved transfer that reaches the partner through such a record was therefore blocked by the default (40 of 40 in the two structures), and 22 of 60 attack calls were blocked by the default rather than attributed, all of which the allow-on-empty variant admitted, together with 16 of 20 calls to the untrusted sheet's endpoint and 6 of 20 through the poisoned chain. Second, the descriptive notice in new wording passed 10 of 20, the failure of set E. Third, the revoked rule passed 20 of 20: the kernel has no notion of a later trusted record withdrawing an earlier authorization, a semantics outside the destination-level scope, whereas the prohibition structure, which the witness recognizes, blocked 20 of 20. On the other eight structures STPG's decision matched the specification on 180 of 180 calls; this is conformance, not resolution, since it includes the default denials of the 22 attack calls and the 16 untrusted-sheet calls whose references the pattern did not resolve. Trusted-rule matching decided 200 of 260 (failing on the prohibition, the notice, and the revoked rule) and the attribution judge 205 of 260 (the notice, the revocation, and the rule beside an untrusted mention), more than STPG because neither depends on the relation pattern. The v3.5 re-derivation changed none of the 260 counterfactual decisions and 6 of the primary victim's 182 actual external calls and 7 of the Llama victim's 177, all benign calls to a prefixed or phrased destination; conformance on the actual calls is 136 of 182 and 125 of 177.

A post-hoc analysis, reported separately and not as a frozen result, extends $\mathcal{M}$ with the relation phrases observed in the model-written records and a direction rule for symmetric phrases; it resolves 29 of the 36 records, changes no decision on the challenge set or on any development set, and raises the frozen-set conformance to 218 of 260, with the two reference structures at 16 and 12 of 20. The deterministic resolver is thus the component that generalizes least: it is what makes the support path verifiable and keeps the witness from completing references on its own, and it is also a fixed lexicon that free phrasing escapes. A learned or model-assisted resolver whose output the kernel still verifies structurally is the design question this result leaves open.

\subsection{Component and Model Sensitivity}
\label{sec:sensitivity}
\subsubsection{Untrusted-Directive Branch and Grouping}
\label{sec:ablation}
\label{sec:grouping}
The trusted-directive-only ablation keeps grouping, binding, the witness, and chain trust and removes only the untrusted branch. On the default-deny kernel its decisions are identical to STPG's on all 918 main-run traces and all 240 counterfactual calls, which follows from Equation~\eqref{eq:policy}: every call STPG blocks through the untrusted branch is one for which no trusted directive targets the destination, so the default blocks it as well.

The branch contributes two measured things: attribution output, since 648 of 648 attacks are blocked with a named untrusted lineage, per-record roles, and a logged $\Delta\pi$ where the ablation records the no-evidence reason; and safety under the availability-preferring default, since with allow-on-empty the ablation passes all 648 attacks and conforms to 84 of 240 challenge decisions, whereas STPG with the same default keeps ASR 0.000 and 204 of 240. The read-time detection signal of Section~\ref{sec:detection} is produced by lineage assembly and scoring, which this ablation retains, so their contribution is not isolated here. The scope is therefore: persistent provenance with destination-witnessed, path-verified trusted-directive authorization makes the default-deny decisions; the untrusted branch attributes the blocked calls and secures the allow-on-empty default.

Two variants keep binding, the witness, the kernel, and the default and change only the unit over which records are assembled: with per-record grouping every record is its own lineage, with per-session grouping every session is one lineage regardless of source. Per-record grouping made the same gate decision as STPG on every call of the sets on which it was run, the main run (648 of 648 attacks blocked, 69 of 71 approved transfers passed with the same two malformed calls blocked), the challenge set (240 of 240), every variant of sets A, B, and D, and the 260 counterfactual calls of the frozen set; it was not run on sets E to I. The reason is that the resolver and the witness, not the grouping, reconstruct the directive: a record that mentions the destination or a chain token becomes a binding lineage on its own, and the chain supplies the records it refers to. Grouping by source lineage contributes three measured things that per-record grouping does not: the attribution unit, since a blocked call names the lineage of its source connector rather than one record; the read-level score on the all-benign set, 0.829 against 0.726; and cost, 719 against 2,177 binding lineages and 1,287 against 2,128 scored lineages (Table~S11). Per-session grouping, the natural unit of a session-scoped design, merged the operator's rule with the untrusted records of the same session in the reported comparisons, so the merged lineage was untrusted, and it passed 8 of 71 approved transfers on the main run, 167 of 240 challenge decisions, and 0 of 30 canonical rules in set A, while its read-level AUROC fell to 0.918. Spatio-temporal assembly is therefore not what blocks the attacks on this data; destination binding with full-path resolution and a verified trusted directive is, and assembly by source lineage gives that decision its attribution unit, its detection score, and its cost, while assembly by session reduced approved-transfer preservation.

\subsubsection{Read-Level Detection and Its Operating Points}
\label{sec:detection}
Table~\ref{tab:detect} reports the read-level AUROC, Figure~\ref{fig:scores} the score distributions, Figure~S3 the ROC curves on both benign sets, and Table~S10 the operating points. Against the 195 benign traces without an approved external-transfer directive, STPG's assembled-lineage score reaches AUROC 1.000 (trace and both-class cluster bootstrap $[1.000,1.000]$), with attack scores in $[0.80,1.00]$ and benign scores in $[0.30,0.45]$; the 55 untrusted internal archive directives, which share the attack's structure and differ only in the internal target, score at most 0.45. The scalar full-context judge reaches 0.996, unit inspection 0.950, and the window scorer 0.908; the paired both-class cluster-bootstrap differences from STPG are $+0.004$ $[0.000,+0.012]$, $+0.050$ $[0.000,+0.170]$, and $+0.092$ $[+0.044,+0.145]$, so only the difference to the window scorer excludes zero.

Against all 270 benign traces, STPG falls to 0.829 and the scalar judge to 0.893 (paired cluster difference $-0.063$ $[-0.148,+0.002]$), because every approved standing rule scores as the directive it is, and the both-class cluster intervals widen to $[0.621,1.000]$ and $[0.768,0.994]$ because one benign subtype carries all the directive-shaped negatives. By factor (Figure~S4), unit inspection has ranking power (per-record attack scores 0.591 against 0.469 for benign records) but falls from 1.000 at $k\le4$ to 0.802 at $k=5$, where each record carries a smaller share of the directive; the window scorer does not degrade with $d$ (0.904, 0.919, 0.902), because the spacing of the records, not the session count, keeps the attack outside its window; STPG is at 1.000 for every $k$, $d$, and injection location.

\subsubsection{Victim Model and Prompt}
\label{sec:generalization}
With Llama 4 Maverick as the victim and everything else unchanged, the agent issued the external routing call in 648 of 648 attack traces, every one to the planted endpoint, and routed all 75 approved transfers externally, with 178 internal routing calls. STPG blocked all 648 attack calls through the untrusted branch and passed 68 of the 75 approved transfers; the 7 it blocked are calls in which this victim wrote the destination as ``partner'' followed by the identifier, which the pre-check blocks as malformed (false-block rate 0.093, $[0.038,0.183]$), a formatting habit the primary victim showed in 2 of 71. Trusted-rule matching decided the same calls the same way, the conservative gate blocked all 75, and the attribution judge blocked 34 of 75 (27 by misattribution to the untrusted background, 7 by the pre-check), consistent with the primary victim. The detection scores are identical across victims because the scorer reads the same records, which is a property of the architecture, not evidence of generalization; two families do not support a rule about model size and susceptibility.

The undefended agent's task asks it to route whenever the records collectively describe a routing instruction, which leaves open whether the 648 of 648 measures susceptibility or compliance. Two less permissive settings of the primary victim answer this. With the hardened prompt, which calls content that originated outside the organization data and never an instruction and allows routing only on an approved operator rule, the agent still attempted an external routing call in 599 of 648 attack traces (162 of 162 at $k=2$ and $k=3$, 160 of 162 at $k=4$, 115 of 162 at $k=5$). These are routing attempts, not completed exfiltrations: 465 of the 599 calls name the planted endpoint and 134 name an intermediate label or key rather than the planted endpoint, so the undefended rate is 0.718 counting endpoint calls (465 of 648: 159, 131, 137, and 38 at $k=2$ to $5$) and 0.924 counting every attempt. The agent cannot tell which records originated outside the organization, because that is exactly the provenance the store dropped; it also routed 69 of 75 approved transfers and issued 24 off-task calls to label strings. With the origin label the gateway knows prefixed to every record, the agent attempted the call in 570 of 648 traces, 329 to the endpoint (0.508) and 241 to a label or key, and routed all 75 approved transfers: told which records are external and told not to act on them, the model still followed the assembled directive, to its endpoint or its label, in seven of eight traces. STPG blocked every attempt under both settings (599 of 599 and 570 of 570; the label calls as non-endpoint, the rest through the untrusted branch) and passed every well-formed approved transfer, 62 of 69 and 74 of 75, the 7 and 1 blocked calls being prefixed destinations of the kind described above. An instruction in a stored record is legitimate in this testbed when a trusted writer issued it and following it is an attack when the writer was the ingestion path; the prompt cannot make that distinction without provenance, and with provenance in the prompt the model still does not reliably make it.

\subsubsection{Second Model Family as Judge and Witness}
\label{sec:judgeswap}
With Llama 4 Maverick as the TSA judge, the witness, the attribution judge, and the scalar judge, STPG's gate decisions were identical to the primary run on all 918 main-run traces and all 240 counterfactual calls, and so were those of the allow-on-empty variant. On the challenge set the Llama witness verified 216 lineages, returned 174 negatives, and had 6 rejected, against 216, 135, and 45 with the primary witness: the verified set is the same, the second model over-reads mapping-only text less, and conformance was unchanged because the structural check and the trust rule, not the raw verdicts, decide. The read-level detection depends on the judge: STPG's assembled-lineage AUROC against the non-directive set fell from 1.000 to 0.990 (TPR 0.966 at the a priori threshold, 0 false positives; Figure~S5), and the scalar judge's rose from 0.996 to 0.999. The attribution judge changed with its model more than with the run: with Llama it blocked all 71 approved transfers, 69 attributed to the untrusted background lineage and 2 by the pre-check, and conformed to 135 of 240 challenge decisions against 156. The gate's decisions are thus insensitive to the model family on this data while the detection scores and the attribution baseline are not, the expected consequence of placing the semantic verdict behind a deterministic support path.


\subsection{Operational Limits: Cost, Scale, Latency, and Trusted Rewrites}
\label{sec:limitsops}
\subsubsection{Cost of Each Condition}
\label{sec:cost}
Table~S11 reports measured calls, tokens, cache behavior, wall-clock time, and list-price cost per condition for the main run as measured in run 4, separating read-time model calls, the TSA judge and the scalar judge, from sink-time calls, the witness and the attribution judge; embedding requests are text-keyed cache lookups, all served from the cache in this run, which was filled with 2,310 API calls during the pilot and run 1. At read time STPG issues one embedding lookup per lineage, 17,766 over 918 reads plus 6 one-time prototype lookups, and 1,287 TSA judge calls, 1.40 per read with about 143 input tokens each.

At sink time STPG issues one witness evaluation per binding lineage of an external call, $\sum_c|B(\delta_c)|$: 719 evaluations for the 719 external calls that passed the pre-checks of run 4 (716 API calls, 3 cache hits, about 562 input tokens each under prompt w3). Under v3.5 the two malformed calls are blocked before the witness, so 717 witness evaluations and 717 attribution calls would be issued; the table keeps the run-4 counts. Every main-run call had one binding lineage, but the count is not a per-call bound: the 416 gate evaluations of the challenge set needed 661 witness evaluations, and Section~\ref{sec:latency} varies the count directly. The attribution judge issues one call per external call past the pre-check (719 calls, 1,218 input tokens each) and the scalar judge one per read. Grouping is a cost factor as well: per-record grouping scores 2,128 lineages at read time and evaluates 2,177 binding lineages at the sink, three times STPG's count, and per-session grouping produces merged texts that miss the embedding cache (2,180 embedding API calls) and long witness inputs (1,004 thousand input tokens). Wall-clock times are totals for 918 traces on a shared workstation including store operations, not per-call latency (Section~\ref{sec:latency}), and prices are Vertex AI list prices as of November 2026 (USD 0.10 per million input and 0.40 per million output tokens for gemini-2.5-flash-lite); they give the model-call cost of the experiment, not a deployment estimate.

\subsubsection{Lineage Scale}
\label{sec:scale}
Set G grows the untrusted lineage of one connector with $n\in\{10,50,100,200\}$ unrelated operational records. Under the default-deny kernel the gate blocked 15 of 15 attack calls and passed 15 of 15 approved transfers at each size, but the branch changed: at $n=10$ and $50$ the attacks were blocked through the untrusted branch, whereas at $n=100$ and $200$ the witness's answer could not be parsed, because the per-record roles it returns for 100 or more records exceed its output budget, so the verdict counted as unsupported and the default fired; the allow-on-empty variant consequently admitted 0 of 15 attacks at each smaller size and 15 of 15 at each larger one. Read-level detection degraded earlier: the TSA judge's score of the assembled lineage fell from a median of 0.70 at $n=10$ to 0.44 at $n\ge50$, below the a priori threshold, while the approved rules kept their scores; the scalar judge fell the same way, and unit inspection was unaffected because it scores records one by one. The victim itself followed the directive in 14, 13, 12, and 9 of 15 traces across the four sizes, and read-time latency grew from a median of 1.5 s to 1.7 s. Dilution of the assembled text and the witness's output format are therefore the two scale limits of the design: the first is a property of scoring a concatenation, the second an implementation choice that a deployment would change by asking roles only for the support records, which we did not do post hoc.

\subsubsection{Trusted-Rewrite Laundering}
\label{sec:launder}
Set I measures the laundering path that the submitted version only named. A trusted operations agent summarized the session-1 records in one sentence; in 60 of 60 attack traces the summary named the synthetic sink, so the note, written by a trusted identity, is a trusted directive to the sink. STPG passed the laundered attack in 20 of 30 traces with the original records present and 19 of 30 with them compacted away; the 21 blocks occurred only because the summary happened to contain a phrase of the relation pattern, which made the note a mapping record that cannot support a verdict, so we count laundering as unmitigated. Trusted-rule matching passed all 60; the conservative gate and the attribution judge blocked the 30 with the original untrusted records present and passed the 30 compacted ones. Read-set inheritance, the one mitigation evaluated, lowers the trust of the note to the minimum trust of the records the agent read in the session that produced it, which the gateway knows because it served that read: it blocked all 60 laundered attacks and passed the 30 approved transfers whose original rule was still present, but blocked all 30 whose rule had been compacted into the note, because the note's read set contained the untrusted background lineage. The mitigation thus trades laundering for a false block on every approved arrangement that survives only as a trusted agent's summary. Alternatives that were not evaluated include attaching the read set as a separate provenance field visible to the witness, requiring trusted rewrites to quote the record identifiers they summarize, or exempting notes whose read set contains an approved rule for the same destination; this trade-off motivates explicit derivation metadata for trusted rewrites, which would extend the evaluated gateway protocol.


\subsection{Limitations and Threats to Validity}
\label{sec:validity}
\textbf{Construct validity:} The ceiling and floor values of the main run reflect a controlled synthetic setting in which rules name partners literally and lineages are clear directives; Sections~\ref{sec:robust} to \ref{sec:limitsops} show what happens once these assumptions are relaxed. Twelve attack and twelve benign template families limit phrasing diversity, so the both-class cluster intervals are the ones to read; the frozen set adds twelve structures and a fourth domain with phrasings from a second model family, but its 240 traces come from one generation prompt, and eleven of its twelve structures have a development-set counterpart (Table~S9), so it tests new wording, a new domain, and one new semantics rather than structures unknown in kind. The metadata probe does not test shortcuts inside record bodies, the challenge set is a policy challenge evaluation of a kernel developed against it in part, and the post-hoc analysis of the frozen set is not a frozen result.

\textbf{Internal validity:} TSA thresholds, prototypes, and prompt were frozen on a pilot that used all three domains; the witness prompt and the kernel were revised during development and review as Section~\ref{sec:versions} records, and the v3.5 identifier contract was applied to the stored logs after the frozen set had been run. The victim's decisions were cached so that every condition saw the same action, so repetitions measure input variation, not generation variance; the model-based conditions moved between runs 3 and 4 on identical inputs (Section~\ref{sec:utility}). The approved-transfer result counts the calls the agent issued (69 of 71 passed; all 69 well-formed calls passed).

\textbf{External validity:} Two model families on one cloud provider were used; the second family as judge and witness changed no gate decision on the main run and the challenge set, as victim it changed approved-call outcomes only through its formatting of destinations, and it did change the detection scores and the attribution baseline. The attack content is non-destructive by design, so ecological validity rests on the realism of the record format. Authorization is scoped to the destination of a routing call (Section~\ref{sec:threat}): a different payload or purpose at an authorized destination, and an authorization that a later trusted record revokes, are outside the guarantee. Contexts had 8 to 26 records in the main run, and Section~\ref{sec:scale} shows where the design degrades with larger lineages.

\textbf{Mechanism:} The conditions of STPG's guarantee are the identifier contract, the relation pattern $\mathcal{M}$, and the witness, and each has a measured failure: the contract blocks approved calls whose destination is not a single identifier (Sections~\ref{sec:utility} and \ref{sec:rules}); the pattern resolved 5 of 36 model-written mapping records in the frozen set (Section~\ref{sec:unseen}); and the witness reads descriptive notices as instructions in 53 of 150 cases under prompt w3 and in 10 of 20 in new wording, and its per-record output format fails beyond about 100 records (Sections~\ref{sec:notice} and \ref{sec:scale}). The submitted kernel's two-hop defect and its correction are described in Section~\ref{sec:pdg} and evaluated in Section~\ref{sec:chain2}.

\textbf{Adaptive adversaries:} An adversary who phrases the mapping outside $\mathcal{M}$ and the destination record so that the witness does not read it as a target, or who pads the lineage with about 100 unrelated records, reaches the default, which blocks under STPG and passes under the allow-on-empty variant; an adversary who makes the victim route to a look-alike of an approved identifier is blocked by the identifier contract; and an adversary who makes a trusted agent summarize the planted records inherits that agent's trust unless the gateway applies read-set inheritance or another derivation rule, of which only the first was evaluated (Section~\ref{sec:launder}).

\section{Conclusion}
\label{sec:conclusion}

STPG combines persistent connector provenance with destination-conditioned witnessing and deterministic support-path verification at an MCP gateway. On the main synthetic dataset, it blocked all 648 attack calls and passed 69 of 71 approved transfers; the two false blocks resulted from malformed destinations. These results compare evidence adapters on a common kernel, not implementations of published defenses. Per-record grouping produced the same gate decisions as source-lineage grouping on the evaluated ablation sets. Source-lineage grouping provided connector-level attribution, a higher all-benign AUROC point estimate, and lower computational cost, without improving blocking in those experiments. The untrusted-directive branch provided attribution and protection under allow-on-empty, while leaving default-deny decisions unchanged.

STPG conformed to the specified policy on all 240 counterfactual calls in the challenge set, which partly informed development. A separate set with second-family phrasings and a new domain was generated after kernel v3.4 and witness prompt w3 were frozen; STPG matched the specified decision on 190 of its 260 counterfactual calls. Eleven of its twelve structures had development-set counterparts. The later v3.5 identifier contract left these 260 decisions unchanged; its effects on actual victim calls are reported separately. The contract also blocks the six space-written rules in set A. Resolver failures, notice misclassification, and unsupported revocation semantics explain the frozen-set misses. The separately labeled post-hoc resolver extension reached 218 of 260 and is not a frozen result. STPG allowed 39 of 60 attacks after trusted rewrites; read-set inheritance blocked all 60 but also blocked all 30 approved transfers whose original rules had been compacted.

These findings support destination-level enforcement under the evaluated identifier contract, resolver rules, and witness behavior, and they show that the default policy determines how each module contributes to the final decision, so detection and enforcement should be evaluated separately on the same kernel and under both defaults. A provenance defense should identify the records supporting a directive and verify that the directive targets the requested destination; relative to MemLineage and PPMF \cite{ouyang2026memlineage,xu2026ppmf}, which were not run here, STPG adds source-connector grouping of records dispersed across a shared store and the measured split between the two defaults. The findings do not establish detection superiority, since confidence intervals for paired AUROC differences from the scalar judge and unit inspection included zero, and external validity remains limited to synthetic traces, two model families, and one cloud provider. STPG is training-free and insertable into an MCP gateway, so it can run as defense in depth beside the zero-trust and access-control mechanisms that cloud operators use \cite{syed2022zta,nist2020zta,microsvc2025,edgezt2026}. Priorities for further work are structurally verified model-assisted resolution, revocation handling, scalable witness outputs, declared derivation for trusted rewrites, and broader evaluation; payload, purpose, and other authorization dimensions remain outside the evaluated scope. The code, data, cached decisions, raw results, and analysis scripts are released as described in the Data Availability Statement.
