\Title{Spatio-Temporal Provenance Guard: Detecting Privilege Escalation Attacks that Exploit Spatio-Temporal Data Loss in Multi-Agent MCP Environments}

\newcommand{\orcidauthorA}{0000-0002-3740-5568}
\newcommand{\orcidauthorB}{0000-0001-6931-2705}
\Author{Deuk-Hun Kim $^{1}$\orcidA{} and Jin Kwak $^{1,*}$\orcidB{}}
\AuthorNames{Deuk-Hun Kim and Jin Kwak}
\address{%
$^{1}$ \quad Department of Cyber Security, Ajou University, Suwon 16499, Gyeonggi-do, Republic of Korea; kimdh1206@ajou.ac.kr (D.-H.K.); security@ajou.ac.kr (J.K.)}
\corres{Correspondence: security@ajou.ac.kr}

\abstract{Multi-agent systems using the Model Context Protocol (MCP) can lose provenance across storage and session boundaries. This spatio-temporal data loss enables an adversary on the ingestion path to distribute an outbound-transfer directive across incomplete records for a privileged agent to assemble and execute. We propose Spatio-Temporal Provenance Guard (STPG), a gateway defense that persists connector provenance, regroups records by source lineage, and authorizes an external routing call only when a trusted directive is witnessed to target that destination and passes a deterministic structural check. Comparisons use evidence adapters on a common kernel, not published defenses. On a Google Cloud testbed with Gemini agents, STPG blocked all 648 attacks and passed 69 of 71 approved transfers. It matched all specified decisions on a policy challenge set and 190/260 on a frozen set from a second model family. Requiring two witness models to agree reduced false authorizations on descriptive notices from 53 to 25 of 150. On a second held-out set generated after all settings were frozen, conformance was 215/260, rising to 229/260 with witness agreement and an extended resolver. Limits remain in reference resolution, descriptive notices, and trusted rewrites, so the results support bounded, destination-level enforcement on synthetic data.}

\keyword{multi-agent systems; Model Context Protocol; data provenance; privilege escalation; AI security}

\section{Introduction}
\label{sec:intro}

Large language model (LLM) agents have evolved from individual tool-using agents into systems of cooperating agents with separate roles \cite{wang2024agents,xi2025rise}. The Model Context Protocol (MCP) standardizes how applications integrate external tools and contextual data \cite{mcpspec}. MCP-based multi-agent deployments have been proposed for security operations \cite{mcpsoc2026}, while zero-trust frameworks are being studied for securing cloud operations \cite{mcloudzt2026}. Interconnection enlarges the attack surface: inter-agent messages, shared stores, delegated privileges, and untrusted content that enters through ingestion paths become points of entry, and indirect prompt injection \cite{greshake2023}, the confused-deputy problem first described by Hardy \cite{hardy1988}, and privilege escalation are among the core threats to agent systems \cite{agentsurvey2026,yao2024survey}.

This paper studies one property of such systems as an attack enabler: data accumulates across storage boundaries and sessions, and the metadata that would tell a later reader where a record came from is often not stored with it. We call provenance loss at storage and session boundaries spatio-temporal data loss: the records persist, but their provenance does not. The spatial dimension is the dispersion of records across injection locations and stores, such as log messages, ticket descriptions, and application programming interface (API) description fields. These records are accessed through different paths. The temporal dimension is their dispersion across sessions that have ended before the records are read. An adversary who controls only an ingestion path can exploit both without writing a complete instruction anywhere: the parts of an outbound-transfer directive are placed in several records that each read as an operational note. When a high-privilege agent later reads the records of a domain into one context, the directive emerges and the agent forwards data to an external destination under its own privilege.

Two questions follow for a defense. The first is whether such an induced transfer can be stopped. In the configurations we evaluate, a gate that keeps provenance across the storage boundary and refuses an external transfer unless a trusted directive authorizes it does so. The second is whether such a gate can be deployed on a path that legitimately reads untrusted data: operations agents read intake notes, vendor advisories, and imported registries as a matter of course, and operators issue approved external transfers such as a standing rule that forwards a weekly report to a partner. A gate that blocks any untrusted influence can reject legitimate operations. A gate that treats a trusted mention as authorization can permit transfers supported only by a registry mention or explicitly prohibited by a rule. At call time, the defense must therefore determine which records formed the directive, whether it targets the requested destination, and whether it is authorized. STPG carries the distinction between provenance and authorization that AuthGraph draws for single executions \cite{wang2026authgraph} across storage boundaries and applies it to the actual destination.

We propose Spatio-Temporal Provenance Guard (STPG), a defense integrated into the MCP gateway. Persistent Provenance Tagging (PPT) stores a provenance sidecar with each record at write time. A sidecar is a metadata record stored alongside the data. Writes from an authenticated source connector share a lineage, and other writes receive individual lineages, so that lineage survives both boundaries. On each read, Temporal Shard Assembly (TSA) groups records by lineage across locations and sessions and scores whether their combined text expresses an external-transfer directive. The Privilege-Delta Gate (PDG) first canonicalizes the call destination and passes destinations on the internal allowlist. For other destinations that pass the endpoint pre-checks, it binds the actual call destination to the lineages that name it, directly or through registry references. A destination-conditioned witness judges whether a binding lineage and its reference-chain records express a directive to that destination, and the kernel checks structural support for that verdict. The kernel passes the call if a supported directive targets the destination and the lineage and its reference chain are trusted. Otherwise, it blocks on destination-specific untrusted directive evidence, or by default when no directive evidence is available. Absence of detection is not treated as authorization.

STPG contributes a threat model for incomplete untrusted records assembled across storage and session boundaries, a gateway mechanism for persistent provenance and destination-specific authorization, and an evaluation that separates attack blocking, approved-transfer preservation, attribution, and operating cost. On the evaluated data, blocking is decided by destination binding and the verified trusted directive and not by assembly: per-record grouping reaches the same gate decisions as source-lineage grouping, and the contribution of source-lineage assembly lies in the attribution unit, the read-level detection score, and the cost of the gate. The comparisons concern evidence adapters on a common kernel. The evaluation includes grouping ablations, a second model family, adverse reference and identifier cases, and two held-out sets of model-written phrasings. The first set was generated after kernel v3.4 and the witness prompt had been frozen. The later v3.5 re-derivation and the post-hoc resolver extension are reported separately. The second set was generated after the witness-agreement criterion and the extended resolver, both motivated by the first set, had been frozen and hashed, and their evaluation on the second set used the fixed settings without further adaptation.

The remainder of this paper is organized as follows. Section~\ref{sec:related} reviews related work. Section~\ref{sec:problem} analyzes the problem and the limitations of existing defenses. Section~\ref{sec:improve} derives the improvements and hypotheses. Section~\ref{sec:method} presents the proposed method, STPG. Section~\ref{sec:exp} describes the experimental setup. Section~\ref{sec:results} reports the experimental results. Finally, Section~\ref{sec:conclusion} concludes the paper.

\section{Related Work}
\label{sec:related}

\subsection{Threats to LLM Agents and Multi-Agent MCP Systems}
Surveys discuss security threats and defenses for LLMs and LLM agents \cite{agentsurvey2026,yao2024survey}. Indirect prompt injection was demonstrated against real LLM-integrated applications \cite{greshake2023} and is benchmarked for tool-integrated agents by InjecAgent \cite{zhan2024injecagent}, whereas the confused deputy predates LLMs \cite{hardy1988}. In these settings the injected instruction is complete within the retrieved content. Multi-agent MCP frameworks for operations, such as the security-operations design of Sim\~oes et al.~\cite{mcpsoc2026}, concentrate on authentication, authorization, and auditing of agent-to-tool traffic.

\subsection{Fragment Assembly and Cross-Session Threats}
\label{sec:rel-assembly}
Liu et al.\ show that summarization-based prompt compression relinks fragments that are each benign in the source into a complete malicious instruction in the summary \cite{liu2026relink}. Their KBRA (Keyed Binding Reassembly Audit) extracts predicate--role--value bindings from source and action, uses provenance-aware channel information with exact or semantic matching, and requires that the bindings behind an action be supported by a single source segment. Relink is the closest mechanism to our assembly condition, but it studies assembly across source fragments at the compression boundary, whereas STPG evaluates authenticated record provenance across storage and application-session boundaries. The unit of KBRA is a source segment, whereas that of STPG is a lineage keyed by the authenticated source connector or by an individual trusted write, with reference chains that may cross lineages.

CSTM-Bench provides cross-session scenarios that accumulate, compose, launder, or inject content at the reader. A reader LLM evaluates these scenarios using the session log and role-specific policies \cite{azarafrooz2026cstm}. XSPI (Cross-Session Stored Prompt Injection) is evaluated in a stateful sandbox with persistent memory and executable tools over 486 cross-session cases \cite{xie2026xspi}. Neither study evaluates the combination used here: record-level storage of writer identity and privilege, approved external transfers as a benign class, and a sink decision that separates induced from authorized transfers, as Section~\ref{sec:data} describes.

\subsection{Provenance and Authorization in Agent Actions}
\label{sec:rel-prov}
\subsubsection{Provenance within One Execution}
CaMeL attaches capabilities that record provenance and permitted readers to every value inside a custom interpreter and checks policies before each tool call \cite{debenedetti2025camel}. AuthGraph separates an injected reasoning graph from an authorization graph built from the user's prompt and checks the allowed origin of each security-critical parameter \cite{wang2026authgraph}. PFI (Prompt Flow Integrity) separates trusted and untrusted agents, checks the source trust of tool outputs, treats unknown sources as untrusted, and keeps an explicit user-approval path across the trust boundary \cite{kim2025pfi}. CapChain combines capability tokens with a signed provenance log that gates state merges in multi-agent workflows \cite{capchain2026}. In all four, provenance lives within one plan, execution, tool call, or state store, and authorization derives from a user prompt, a capability policy, or a user approval. In STPG the producer provenance is persisted with the record, attributed to an authenticated principal with a trust level, and re-read in a later session by a different agent for which no per-request user prompt exists. Our ephemeral-taint condition reproduces only a taint that is not persisted at the storage boundary, not PFI or CaMeL.

\subsubsection{Persistent Provenance with Action Authorization}
Three recent preprints combine persistent provenance with action authorization \cite{ouyang2026memlineage,xu2026ppmf,maloyan2026sleeper}.
MemLineage maintains an append-only log of entries signed with per-principal keys and a derivation graph. Each entry inherits the least trust among the parents connected to it by sufficiently strong derivation edges. Its sensitive-action gate specifies which source classes may authorize each governed parameter. On a deterministic harness, it reports zero attack success and a 100\% legitimate-dispatch rate \cite{ouyang2026memlineage}. PPMF maintains platform-maintained provenance with source and confirmation labels. It binds the canonical target of an action to supporting memory entries, resolves aliases only through a platform mapping, and retains all candidates when the match is ambiguous. Authorization uses the minimum trust of this support. Under intact provenance, PPMF reports zero attack success and 100\% benign success \cite{xu2026ppmf}. Sleeper Channels tags artifacts by channel, principal, and device, closes memory operations over their causal sources, and allows an action when its causal set is entirely trusted or an owner grant bound to the action digest exists. Its evaluation is preregistered as follow-on work \cite{maloyan2026sleeper}.
Two of their mechanisms are close to ours: the alias resolution and all-candidates rule of PPMF correspond to the reference resolution and ambiguity rule of STPG, and the per-parameter authority of MemLineage to the destination-level scope of STPG. The differences we claim are narrower than a new principle. First, STPG groups records that other principals write to a shared store by the authenticated source connector, so that records dispersed over locations and sessions are regrouped as one lineage; none of the three evaluates this grouping. Second, the authorization evidence in STPG is a directive found in the stored records themselves, such as an operator's standing rule, that must be witnessed to target the destination of the actual call, with mention, mapping, and prohibition in the same text distinguished from instruction, and verified against a deterministic support path. Third, the evaluation covers mixed trusted and untrusted directives in one context under both empty defaults, with the untrusted branch isolated by ablation.

\subsubsection{Other Related Areas}
Classical information-flow control \cite{denning1976,sabelfeld2003} and the provenance literature \cite{provsurvey2023,li2021provgraph} provide the lattice and the tracking machinery but do not define which records formed an LLM agent's directive or whether it was authorized for the destination it reached. Layered prompt-injection defenses \cite{spotlight2026} and recursive log-analysis frameworks \cite{logresp2025} inspect content or behavior and are complementary to a gate at the sink.

\section{Problem Analysis and Limitations of Existing Defenses}
\label{sec:problem}

\subsection{System Model}
\label{sec:system}
A multi-agent MCP environment consists of agents $a$ with a trust level $\tau(a)$ and a privilege level $\pi(a)$, an MCP gateway through which every write, read, and tool call passes, and a shared store of records. We use four trust levels, $\tau_{\mathrm{ext}}<\tau_{\mathrm{ingest}}<\tau_{\mathrm{ops}}<\tau_{\mathrm{sys}}$, and four privilege levels, read, write, API, and Identity and Access Management (IAM). An ingest agent with trust $\tau_{\mathrm{ingest}}$ and privilege write writes content that enters through an ingestion endpoint, and such content is assigned source trust $\tau_{\mathrm{ext}}$ regardless of the writer. An operations agent with trust $\tau_{\mathrm{ops}}$ and privilege IAM periodically reads the accumulated records of a domain in one read and decides its next step: a status report or a routing action that names a destination, internal if on an approved allowlist and external otherwise. Privilege separation is enforced by identity: the two agents run under separate service accounts, the gateway refuses a tool outside the caller's profile, labels each write with the identity and endpoint through which it arrived, and refuses the call from the ingest identity to the privileged routing tool. A session is an application-level unit, one run of an agent against the gateway with its own identifier, and it does not depend on how the MCP transport tracks connections. The agent carries no memory across sessions, and the store persists.

\subsection{Threat Model}
\label{sec:threat}
The adversary controls the external ingestion path only. It can insert records whose bodies read as operational notes, but it cannot change model weights, system prompts, the gateway, or the provenance sidecars, and it cannot forge the source identifier, which the gateway derives from the authenticated ingestion connector. Within this capability, the attack satisfies four conditions, which Figure~\ref{fig:threat} places on the two axes of the data loss.
\begin{enumerate}
\item \textbf{Individually incomplete:} No single one of the $k$ records names both an action and an external target. The term does not mean statistically indistinguishable. Section~\ref{sec:detection} reports that per-record scores separate the classes in part.
\item \textbf{Emergent on assembly:} The destination of the transfer is determined only when the references in the records are resolved together. A single record may still read as an instruction without a resolvable target, which Section~\ref{sec:rules} measures, so what the assembly adds is the destination, and attribution of that destination, not merely the detection of an instruction, is what a defense must decide on.
\item \textbf{Spatio-temporally dispersed:} Spatially, the records are spread over injection locations and stores such as log messages, ticket descriptions, and tool description fields. Temporally, they are spread over $d$ sessions, with ordinary records between them. A reader that groups by location, window, or session sees fragments, whereas grouping by source reunites these records across locations and sessions.
\item \textbf{Low trust to high privilege:} The records have source trust $\tau_{\mathrm{ext}}$ and the action is executed with privilege IAM. The privilege gap $g\in\{0,1\}$ states whether the writing identity also has lower privilege than the caller, $g=1$, which is a privilege escalation across identities, or is a high-privilege identity whose ingestion-path write is nevertheless untrusted, $g=0$, which is an induced unauthorized action. We report both and do not equate them.
\end{enumerate}

The same context may also contain an approved external transfer, a trusted operator's standing rule naming a partner, and the defense must separate the two external calls, as Section~\ref{sec:holdout} describes. The attack depends on the loss of provenance, not on the detectability of any single record.

\textbf{Scope of the guarantee.} The defense decides the destination of a privileged routing call and nothing else. The guarantee also assumes that trusted writers do not rewrite untrusted content into records of their own: a workflow in which a trusted agent summarizes or transforms untrusted records is outside the evaluated guarantee, and Section~\ref{sec:launder} measures the exposure and one mitigation. An authorized destination is one that a trusted directive targets. A trusted directive authorizes every call to its destination from the same context, including calls induced by an untrusted directive to that destination. The gate does not inspect the payload, amount, period, or purpose of the call. It therefore does not cover misuse of an authorized destination with a different payload or purpose, or destinations whose authorization a trusted record has subsequently revoked. Section~\ref{sec:unseen} measures the second case and Section~\ref{sec:validity} states both.

\subsection{Limitations of Existing Defenses}
\label{sec:limits}
Each threat condition exploits a limitation of existing defenses, which a comparison condition instantiates on the common kernel and a factor or challenge structure stresses, as Table~S1 lists. Three limitations concern what a defense can see and keep. A bounded window cannot contain a directive whose records lie outside it. Provenance that lives inside one execution leaves the gate with no lineage once a record crosses the storage boundary, which is a property of non-persistence rather than of PFI or CaMeL specifically. Lexical signatures do not fire on lexically ordinary records. Three further limitations concern the decision. A gate that uses untrusted influence without attribution blocks every external call that any untrusted record touched. A gate that authorizes a call because a trusted record names its destination takes a mention for an authorization. A gate that checks the existence of a directive and the occurrence of the destination separately can be steered by a trusted rule that forwards to A while listing or prohibiting B. STPG is designed against the last three.

\section{Derivation of Improvements}
\label{sec:improve}

These limitations lead to three design requirements and four hypotheses, each stated for the conditions evaluated rather than for defenses in general.

\subsection{R1: Bind Provenance to Data at Write Time and Persist It across Both Boundaries}
In-execution taint cannot be reconstructed after the fact, so the source identity, the writer, and the writer's trust and privilege must be stored as a sidecar that any later reader in any session can resolve, whatever location the record was hidden in. Hypothesis H1: among the evaluated configurations, every condition that persists provenance and applies the default-deny kernel blocks the attack, and the ephemeral-taint configuration, which persists nothing and passes on empty evidence, does not. H1 compares configurations, not persistence alone: a gate with no provenance and the default-deny kernel would also block every external call, including the approved ones, and persistence is what lets a gate pass approved work selectively.

\subsection{R2: Attribute the Actual Call to Lineages, Witness the Destination, and Decide on Trust}
Authorization must inspect a source lineage together with its reference chain because the destination may be resolved across records, so the unit of judgment is the set of records that share a source lineage. A context can contain both approved and induced transfers. The gate must therefore bind the actual call destination to the lineages that name it, resolving registry references across lineages where necessary. It must then establish that a binding lineage directs a transfer to that destination. It is insufficient merely to find a directive somewhere in the lineage and a separate occurrence of the destination string. A trusted record that mentions, lists, or prohibits the destination is not an authorization, and absence of a directive provides no authorization either. Hypothesis H2: at equal attack blocking, STPG passes approved external transfers by positive attribution to a trusted directive, whereas the conservative gate and a full-context attribution judge block some or all of them. Hypothesis H3: on mixed, cross-referenced, poisoned, degraded, same-record, ambiguous, and off-task structures, STPG makes the specified decision for each listed destination, whereas trusted-rule matching passes unauthorized transfers and the conservative gate blocks approved ones. H3 is a policy-conformance statement that includes default-deny outcomes and the deliberate denial of approved transfers that the policy excludes.

\subsection{R3: Measure Directive Emergence Semantically and State What It Does Not Exclude}
Records are lexically ordinary, so the scorer must judge whether an assembled text functions as an external-transfer instruction. Hypothesis H4: the assembled-lineage score separates attacks from hard benign negatives that share the surface form of the attack, with an operating point that transfers across held-out domains without retuning. A metadata-only probe finds no consistent cross-domain advantage and does not exclude text shortcuts, and we report where it finds template fingerprints.

PPT implements R1, TSA implements the assembly and scoring aspects of R2 and R3, and PDG implements the binding, witnessing, and decision aspects of R2. The modules can be integrated into an MCP gateway without retraining a model. At read time, TSA performs an embedding lookup for each lineage and calls its second-stage judge only for lineages that pass the embedding filter. At the sink, STPG requires one witness evaluation per binding lineage before caching, giving a total of $\sum_c |B(\delta_c)|$ over the external calls that pass the endpoint pre-checks.

\section{Proposed Method: STPG}
\label{sec:method}

\subsection{Overview}
Figure~\ref{fig:overview} shows STPG inside an MCP gateway: PPT on the write path, TSA on the read path, PDG on the sink path. The two dimensions of the data loss map onto the modules: PPT keys provenance by source so that the spatial dispersion over locations and stores is undone by one lookup, and TSA groups by lineage rather than by window or session so that the temporal dispersion over sessions is undone at read time. STPG sees only record bodies and the provenance PPT produced, whereas the evaluation harness keeps ground-truth labels in a separate table that no module reads.

\subsection{PPT: Persistent Provenance Tagging}
\label{sec:ppt}
On each write, PPT stores the sidecar $\langle \mathrm{id}, \tau_{\mathrm{src}}, w, \tau(w), \pi(w), t, \sigma, \ell\rangle$. Its fields are the record identifier, the source trust, the writer $w$ with its trust and privilege, the time, the session $\sigma$, and the lineage key. The source trust $\tau_{\mathrm{src}}$ is $\tau_{\mathrm{ext}}$ for writes through an ingestion endpoint and $\tau(w)$ otherwise. The lineage key $\ell$ is defined by
\begin{equation}
\ell =
\begin{cases}
\texttt{src:}\,r & \text{if the gateway attached an authenticated source connector identifier } r,\\
\texttt{write:}\,\mathrm{id} & \text{otherwise}
\end{cases}.
\label{eq:lineage}
\end{equation}
As a result, records from one external source share one lineage across sessions and stores, while every other write, including each write of a trusted agent, is its own lineage. A trusted directive that spans two records is authorized only if the second record is reached by reference resolution, as Section~\ref{sec:pdg} describes. Grouping internal writes by session was rejected because it merges an operator's directive with unrelated status records and dilutes the text that TSA scores.

The source identifier and the writer identity are issued by the gateway from the authenticated connector and the calling service account, not from the record body, so the adversary of Section~\ref{sec:threat} cannot set, rotate, or omit them. Provenance is stored in a table keyed by record identifier, so a read in session $\sigma_j$ resolves a record written in $\sigma_i<\sigma_j$ from any store or field without state carried in the agent. The influencing records of a sink call are all records returned by the read that formed the agent's context. A record without a sidecar forms its own lineage, keyed unknown:id, with source trust $\tau_{\mathrm{ext}}$, and the challenge set tests the missing-sidecar cases directly. A trusted agent that rewrites untrusted content gives the rewrite its own trust, a laundering path studied for agent memory by PPMF \cite{xu2026ppmf} and measured in Section~\ref{sec:launder}.

\subsection{TSA: Temporal Shard Assembly}
\label{sec:tsa}
On every read, TSA regroups the returned records by lineage key. Neither recency, position, location, nor session plays a role. The grouping key is a parameter of the gateway: STPG groups by lineage, and Section~\ref{sec:grouping} evaluates per-record and per-session grouping with every other component unchanged. For each lineage $G$ it joins the bodies in storage order and computes the directive score $E(G)\in[0,1]$ with a two-stage scorer: the first stage maps the cosine similarity between the embedding of the assembled text and six fixed abstract prototypes of forwarding output externally to $[0,1]$. The prototypes were written independently of the attack phrasing and are released with the code. TSA uses the first-stage score when it is below $\theta_1$. Otherwise, an LLM judge assesses the extent to which the lineage expresses a complete external-transfer instruction. A lineage is a directive when $E(G)\ge\tau_{\mathrm{TSA}}$, and the read-level detection signal is $E^{*}=\max_G E(G)$, as Algorithm~\ref{alg:tsa} summarizes. $E(G)$ measures whether a directive to transfer data externally has formed, not whether it is authorized or which destination it targets, so an approved standing rule also scores high, and Section~\ref{sec:detection} reports detection against both benign sets for this reason. The scores, $F$, $\theta_1$, and $\tau_{\mathrm{TSA}}$ are read-time outputs and not inputs of the sink decision: the witness of Section~\ref{sec:pdg} receives the lineage grouping and the texts, not the scores. With $q$ lineages in a read, the cost is at most $q$ embedding lookups, cached by text, and one judge call per lineage that passes the first stage.

\begin{algorithm}[H]
\caption{TSA on a read of records $R$ with provenance store $P$}
\label{alg:tsa}
\begin{algorithmic}[1]
\STATE $\mathcal{G} \leftarrow \emptyset$
\FORALL{$r \in R$}
  \STATE $p \leftarrow P[r.\mathrm{id}]$; \textbf{if} $p$ is undefined \textbf{then} $p.\tau_{\mathrm{src}}\leftarrow\tau_{\mathrm{ext}}$, $p.\ell\leftarrow\texttt{unknown:}r.\mathrm{id}$
  \STATE append $r$ to $\mathcal{G}[p.\ell]$
\ENDFOR
\STATE $F\leftarrow\emptyset$; $E^{*}\leftarrow 0$
\FORALL{$G \in \mathcal{G}$}
  \STATE $x \leftarrow$ join of the bodies of $G$ in storage order; $e_1 \leftarrow \mathrm{EmbeddingScore}(x)$
  \STATE $E(G) \leftarrow e_1$ \textbf{if} $e_1 < \theta_1$ \textbf{else} $\mathrm{JudgeScore}(x)$
  \STATE $E^{*}\leftarrow\max(E^{*},E(G))$
  \STATE \textbf{if} $E(G)\ge\tau_{\mathrm{TSA}}$ \textbf{then} $F\leftarrow F\cup\{G\}$
\ENDFOR
\RETURN $R$, $E^{*}$, $\mathcal{G}$, $F$
\end{algorithmic}
\end{algorithm}
\subsection{PDG: Privilege-Delta Gate}
\label{sec:pdg}

\subsubsection{Binding and Reference Resolution}
When the operations agent with privilege $\pi_c$ issues a call with destination $\delta$, PDG first applies the identifier contract to $\delta$ and to every identifier it compares against. An endpoint identifier is one token. After the wrapping is stripped, namely surrounding quotes and backticks, a trailing parenthesized annotation, and trailing punctuation, a well-formed destination contains no whitespace, quotes, or brackets. A string that does is a phrase, not an identifier, and is blocked as malformed before any other step, as Section~\ref{sec:precheck} describes. The canonical form of a well-formed identifier, which is also the equivalence the mock backend applies when it routes, folds case and collapses every run of hyphens and underscores into one hyphen. Two identifiers denote the same destination if and only if their canonical forms are equal, and a mention in a record is an occurrence of the canonical identifier at identifier boundaries with hyphens and underscores interchangeable. Thus PARTNER-EXT-897, partner\_ext\_897, and Partner-Ext-897 (ext) are one destination, whereas PARTNER-EXT-8970, PARTNER-INT-897, and X-PARTNER-EXT-897 are others, and PARTNER EXT 897 or partner PARTNER-EXT-897 is not a destination at all. Whitespace is a word boundary and never an identifier separator, so the contract and the matcher coincide. In kernel v3.4, the matcher also folded spaces. It therefore accepted the literal destination ``partner registered under key contact\_sec'' when the same phrase appeared in the operator's rule, although the key had not been resolved. Section~\ref{sec:confusable} evaluates the three malformed forms the victims issued, and Section~\ref{sec:rules} reports the cost of the contract on rules whose authors write an identifier as separate words. PDG then determines which lineages name $\delta$. A lineage binds $\delta$ directly if $\delta$ occurs in its text, and by reference if the context contains mapping records that resolve a token to $\delta$ and the lineage mentions that token. Mapping records are those that match the relation pattern $M$, whose forms are ``key = $\delta$'', ``label maps to key'', ``label resolves to $\delta$'', and ``label is bound to $\delta$''. The resolver follows at most two hops over all records of the context and records, for every token it reaches, the parent of that token toward $\delta$. The records of the whole path from the mentioned token down to $\delta$ form the chain $C(G,\delta)$, which may lie in other lineages, and the tokens reached form the admissible token set $T(\delta)=\{\delta\}\cup\{\text{chain tokens}\}$. The trust of a binding and its ambiguity are computed over the entire path: a token with two conflicting values is ambiguous, a path that contains an ambiguous token at any hop is ambiguous, and a lineage that reaches $\delta$ only through an ambiguous path is treated as an untrusted binding whatever its own trust. A token that requires more than two resolution hops or lies on a cycle remains unresolved and creates no binding. Binding is a set computation and does not depend on scores, ties, or visiting order.

The critical case is a trusted directive that names label A, a trusted mapping from A to key B, and an untrusted mapping from B to an external endpoint. Resolution from the endpoint reaches B at hop one through the untrusted record and A at hop two through the trusted record, with B as the parent of A. The directive mentions A, so $C$ contains both mapping records, $\tau_{\min}$ is the trust of the untrusted endpoint mapping, and the call is blocked as an untrusted directive. Kernel v3.3 returned only the record of the mentioned token, so the endpoint mapping dropped out of the trust computation and the same call appeared trusted. Kernel v3.4 corrected this defect, and every reported run was recomputed on the corrected kernel. Section~\ref{sec:chain2} evaluates untrusted, missing, and conflicting mappings at both hops.

\subsubsection{Endpoint Pre-Checks}
\label{sec:precheck}
The routing argument must be a final endpoint. After canonicalization, destinations on the internal allowlist pass. For all other destinations, two pre-checks run before evidence-based authorization. They reject malformed destination strings and identifiers that the available context explicitly resolves to another value, and they do not establish whether an otherwise unresolved token denotes a deliverable endpoint. The first is the grammar check of the identifier contract: a destination that is not a single identifier after its wrapping is stripped, because it contains whitespace, quotes, or brackets, is blocked as malformed. This check depends on the destination string alone and precedes every model call. It is also the point at which a deployment would return the call to the agent for correction, since the block carries the reason. The second is decided from the context rather than from a list of known strings: if the context itself resolves $\delta$ to something else through a record of the form $\delta\ M\ X$, then $\delta$ is a label or a registry key, and the call is blocked as non-endpoint. Both pre-checks are part of the kernel and are applied by every condition that has a gate input, which excludes only the undefended agent and the ephemeral-taint proxy.

\subsubsection{Witness and Support-Path Verification}
\label{sec:witness}
Binding links a destination to a lineage without establishing whether the lineage instructs a transfer there. For example, a trusted rule that authorizes forwarding to A but retires B binds both destinations. PDG therefore asks a destination-conditioned witness, an LLM with a fixed prompt released with the code: given the numbered records of $G\cup C(G,\delta)$ and $\delta$, does a record contain an instruction or standing rule to forward, route, mirror, or deliver output whose target is $\delta$, directly or through a label or key that the given records resolve? The witness returns three outputs: a raw verdict $W_{\mathrm{raw}}$, a role for each record, and a support list $S$. The possible roles are target, mapping, mention, prohibited, and none. The kernel accepts the verdict only if it is supported by an admissible path, which it checks itself:
\begin{equation}
W^{*}(G,\delta)= W_{\mathrm{raw}}\ \wedge\ \exists\, r\in \mathrm{Cand}:\ \neg\,\mathrm{map}(r)\ \wedge\ \mathrm{mentions}(r, T(\delta)).
\label{eq:verify}
\end{equation}
Here, $\mathrm{map}(r)$ is true when record $r$ matches the relation pattern $M$ that the resolver uses, so a mapping record cannot serve as the supporting instruction. The predicate $\mathrm{mentions}(r,T)$ is true when $r$ names $\delta$ or an admissible chain token. If $S$ is nonempty, $\mathrm{Cand}=S$. Otherwise, $\mathrm{Cand}$ contains the records assigned the role target, and if there are none, it contains all records in $G\cup C$. A raw-true verdict that fails Equation~\eqref{eq:verify} is recorded as unsupported and treated as false. The verification is structural: it establishes that the verdict rests on an admissible non-mapping record that names the destination or a chain token, and it does not independently establish the semantic validity of the authorization, which remains the judgment of the witness. Section~\ref{sec:agreement} therefore evaluates a stricter semantic criterion in which two witnesses of different model families must agree.

The roles are therefore advisory: the semantic verdict comes from the model and the path from the kernel, and the witness cannot complete an unresolved reference, pull in records outside the chain, or promote a mapping record to an instruction. Prompt version w3, used in runs 4 and 5, adds one clause to the earlier prompt: a record that only states who a partner, recipient, or contact is, or where something is normally kept, describes a fact and takes the role mention, whereas a standing arrangement that commits output to be sent is an instruction. Section~\ref{sec:notice} measures the effect of this clause. Verdicts are cached by prompt version, model, numbered record text, and destination, so every condition that uses the witness receives the same answer for the same input.

\subsubsection{Decision Kernel}
With $B(\delta)$ the binding lineages and $\tau_{\min}(G)$ the minimum source trust over $G\cup C(G,\delta)$, where $C$ holds every record on the resolution paths, with a missing sidecar and an ambiguous path both counted as $\tau_{\mathrm{ext}}$:
\begin{equation}
\mathrm{dec}(\delta)=
\begin{cases}
\mathrm{PASS} & \mathrm{canon}(\delta)\in\mathcal{D}_{\mathrm{int}}\ \text{(internal)},\\
\mathrm{BLOCK} & \delta \text{ is not a single identifier (malformed)},\\
\mathrm{BLOCK} & \delta \text{ resolves further in the context (non-endpoint)},\\
\mathrm{PASS} & \exists\, G\in B(\delta):\ W^{*}(G,\delta)\ \wedge\ \tau_{\min}(G)\ge\tau_{\mathrm{ops}}\ \text{(trusted)},\\
\mathrm{BLOCK} & \text{else if }\exists\, G\in B(\delta):\ W^{*}(G,\delta)\ \wedge\ \tau_{\min}(G)\le\tau_{\mathrm{ingest}}\ \text{(untrusted)},\\
\mathit{empty} & \text{otherwise (no evidence; STPG: BLOCK)}.
\end{cases}
\label{eq:policy}
\end{equation}
Algorithm~\ref{alg:gate} gives the pseudocode of the STPG realization of the kernel. Figure~\ref{fig:kernel} shows this decision flow together with the adapters of Section~\ref{sec:adapters}, and Table~S2 lists an example context for each row of Equation~\eqref{eq:policy}. Authorization is conditioned on the destination and evaluated per lineage: a context with a trusted rule to A and an induced directive to B passes a call to A and blocks a call to B. The challenge set covers this distinction when an untrusted lineage holds a directive to B and a mention of A beside a separate trusted rule to A, and when one trusted record authorizes A but prohibits B. A trusted directive that targets $\delta$ authorizes $\delta$ even if an untrusted directive also targets it. The scope is the destination of a routing call, not payloads, periods, or amounts, and the untrusted directive is logged. A directive whose chain passes through an untrusted, missing, or ambiguous record is untrusted.

The empty default is BLOCK for STPG. The pass default is evaluated as a separate condition because a deployment that prefers availability may choose it, and its cost is measured rather than assumed. For decisions supported by evidence, we log $\Delta\pi=\pi_c-\min\pi(w)$, using the integer ranks $\mathrm{read}<\mathrm{write}<\mathrm{API}<\mathrm{IAM}$ of the writers in the evidence lineages and their chains, and we log NA when no evidence is available. A blocked event with $\Delta\pi>0$ is classified as privilege escalation across identities, and one with $\Delta\pi=0$ as an induced action. This value is diagnostic and does not affect the decision, and the name of the module refers to this attribution.

\begin{algorithm}[!htb]
\caption{STPG realization of the decision kernel at a privileged routing call, with adapters and defaults as listed in Table~\ref{tab:adapters}}
\label{alg:gate}
\begin{algorithmic}[1]
\REQUIRE destination $\delta\neq\varnothing$, lineages $\mathcal{G}$, caller privilege $\pi_c$, evidence adapter, default $\mathit{empty}\in\{\mathrm{BLOCK},\mathrm{PASS}\}$
\STATE $\delta\leftarrow\mathrm{canon}(\delta)$ \COMMENT{strip wrapping, fold case, collapse runs of \texttt{-} and \texttt{\_} to one \texttt{-}}
\IF{$\delta\in\mathcal{D}_{\mathrm{int}}$} \RETURN PASS \ENDIF
\IF{$\delta$ contains whitespace, quotes, or brackets} \RETURN BLOCK (malformed) \ENDIF
\IF{$\exists\, r\in\bigcup\mathcal{G}:\ r \text{ matches } \delta\ M\ X$} \RETURN BLOCK (non-endpoint) \ENDIF
\STATE $\mathit{chain}\leftarrow\mathrm{Resolve}(\delta,\bigcup\mathcal{G})$; $T\leftarrow\{\delta\}\cup\mathrm{keys}(\mathit{chain})$ \COMMENT{$\le 2$ hops; each token keeps its parent, its path to $\delta$, and the ambiguity of the path; cycles or deeper $\Rightarrow$ unresolved}
\STATE $\mathcal{T}\leftarrow\emptyset$; $\mathcal{U}\leftarrow\emptyset$
\FORALL{$G\in\mathcal{G}$}
  \STATE $(\mathit{bound},C,\mathit{amb})\leftarrow\mathrm{Bind}(G,\delta,\mathit{chain})$ \COMMENT{$C$ = all records on the paths of the tokens $G$ mentions; $\mathit{amb}$ over those paths}; \textbf{if} \NOT $\mathit{bound}$ \textbf{then continue}
  \STATE $(w,\mathit{roles},S)\leftarrow\mathrm{Witness}(G\cup C,\delta)$ \COMMENT{adapter-specific; STPG: LLM witness}
  \STATE $\mathrm{Cand}\leftarrow S$ \textbf{if} $S\neq\emptyset$ \textbf{else} $\{r:\mathit{roles}[r]=\mathrm{target}\}$ \textbf{if} non-empty \textbf{else} $G\cup C$
  \STATE $w\leftarrow w\ \wedge\ \exists r\in\mathrm{Cand}:\ \neg\mathrm{map}(r)\wedge\mathrm{mentions}(r,T)$ \COMMENT{Equation~\eqref{eq:verify}; failure logged as unsupported}
  \STATE \textbf{if} \NOT $w$ \textbf{then continue}
  \STATE $\tau\leftarrow\min_{r\in G\cup C}\tau_{\mathrm{src}}(r)$; \textbf{if} $\mathit{amb}$ \textbf{then} $\tau\leftarrow\tau_{\mathrm{ext}}$
  \STATE \textbf{if} $\tau\ge\tau_{\mathrm{ops}}$ \textbf{then} $\mathcal{T}\leftarrow\mathcal{T}\cup\{G\}$ \textbf{else} $\mathcal{U}\leftarrow\mathcal{U}\cup\{G\}$
\ENDFOR
\STATE $\Delta\pi\leftarrow\pi_c-\min\pi(w)$ over writers of $\mathcal{T}\cup\mathcal{U}$ and their chains if non-empty, else NA; log
\IF{$\mathcal{T}\neq\emptyset$} \RETURN PASS (trusted-authorized) \ENDIF
\IF{$\mathcal{U}\neq\emptyset$} \RETURN BLOCK (untrusted-directive, or ambiguous-reference) \ENDIF
\RETURN $\mathit{empty}$ (no-evidence)
\end{algorithmic}
\end{algorithm}

\section{Experimental Setup}

\subsection{Testbed and Models}
\label{sec:testbed}
The experiments run against a Google Cloud project that mirrors a multi-agent MCP deployment: an MCP gateway service, a document store for records and provenance, an analytics store for traces, and a message bus for inter-agent events, with separate service accounts for the ingest and operations agents. The agents use Gemini models on Vertex AI in the us-central1 region. The model gemini-2.5-flash-lite is used for the primary victim agent, the TSA judge, the witness, the scalar full-context judge, and the attribution judge, and text-embedding-005 provides embeddings. A second model family, Llama 4 Maverick, an open-weight Meta model with 17B active parameters and 128 experts, is served through the Vertex AI model-as-a-service endpoint in region us-east5. It is used as the judge, witness, attribution judge, and scalar judge in place of gemini-2.5-flash-lite in Section~\ref{sec:judgeswap}, as the victim in Section~\ref{sec:generalization}, and as the author of the phrasings of the frozen evaluation set in Section~\ref{sec:unseen-design}. Every model call goes through one backend module, so a model is swapped by name without changing prompts, parsing, or caching. All generation runs at temperature 0 with the optional reasoning mode of the models disabled so that the output budget is spent on the JSON answer. The victim's decision for each trace is generated once and cached, so every condition sees the identical agent action. The gateway implements the tool, resource, and session primitives of MCP specification revision 2025-06-18. Later revisions \cite{mcpspec} change the transport, handshake, and discovery mechanisms, not the write, read, and tool-call paths that the gateway intercepts.

The primary comparisons hold model and platform settings fixed and share cached victim actions and token accounting. A separate sensitivity study substitutes Llama 4 Maverick while retaining the platform and evaluation pipeline. This design controls platform-related variation but limits external validity to two model families on Google Cloud, as Section~\ref{sec:validity} discusses. The exact model identifiers and the version history of the runs are listed in Table~S6. The role of each model, whether victim, TSA judge, or witness, is stated where the condition is defined in Section~\ref{sec:conditions}.

\subsection{Data Generation and Hygiene}
\label{sec:data}

\subsubsection{Why Synthetic Data}
The two public cross-session resources do not contain the factors the hypotheses need to control together, as Table~S4 summarizes. CSTM-Bench provides cross-session scenarios with hard benign confounders and per-role policies, but it does not evaluate a shared store with stored writer identity and privilege and a privileged sink to gate \cite{azarafrooz2026cstm}. XSPI-Bench provides stored-injection cases with executable tools, but it does not model writer privilege as a stored record attribute or approved external transfers as a benign class \cite{xie2026xspi}. We therefore generate traces on one kernel with a mock sink that records call arguments. Destinations are synthetic placeholders and no data leaves the testbed, following the non-destructive conventions of agent-security benchmarks \cite{zhan2024injecagent}. Three operational domains, incident handling, billing settlement, and access review, provide the vocabulary, and records imitate the field structure of cloud logs, tickets, and registry entries that log-analysis agents read \cite{logresp2025}.

\subsubsection{Attack and Benign Traces}
The attack design crosses the record count $k\in\{2,3,4,5\}$, the session count $d\in\{1,3,5\}$, the privilege gap $g\in\{0,1\}$, three injection locations, and three domains. Three repetitions per combination yield 648 traces. Each trace consists of one read of 8 to 26 records. The $k$ attack records are separated by trusted filler records at a spacing that increases with $d$, records are assigned to $d$ sessions by position, and one neutral operator note is inserted at a random position. The attack texts come from twelve template families, three domains times four values of $k$. Repetitions vary the destination identifier, the filler sample, positions, session assignment, and note position, so the 648 traces are not independent texts, a point to which Section~\ref{sec:stats} returns. No single attack record names both an action and an external target.

Benign traces, 90 per domain and 270 in total, draw their length, session count, and untrusted-lineage size from the same distributions and come in four subtypes: 75 approved external transfers, each an operator's standing rule naming a partner; 65 approved internal directives; 55 untrusted archive directives to an approved internal destination; and 75 index-note traces without any directive. Every benign trace contains one untrusted background lineage of $k_b\in\{2,\dots,5\}$ records written through the ingestion connector. The record texts mirror the attack templates record by record, using operating rules, binding notes, registry entries, policy references, and directory lines, but resolve to an internal store. The background lineages belong to one of two families, an internal archive directive, family A, or a descriptive index note, family B. These hard negatives make the approved external transfer a test of attribution: its context contains an untrusted lineage of the form the attacks use, and the only difference is which lineage is the directive behind the call. Benign texts come from twelve template families as well, four subtypes times three domains.

\subsubsection{Metadata-Only Probes and What They Do Not Show}
To test whether data-generation artifacts predict the label without access to any record body, we trained a logistic regression, a depth-3 tree, and a gradient-boosted ensemble on 19 metadata features per trace, with AUROC (Area Under the Receiver Operating Characteristic Curve) computed per fold and reported in Table~S5. The features are counts of records, sessions, lineages, untrusted records and lineages, and injection locations, the positions of the first and last untrusted record, and text-length statistics. Across domains the metadata do not transfer: leaving one domain out, the fold AUROCs range from 0.30 to 0.52, and label permutation gives means near 0.50. The below-0.5 folds indicate a feature direction that reverses between domains. Within a domain, text length identifies template families: leaving one attack family out, the ensemble reaches a mean AUROC of 0.701, 0.708 with the four length features alone and 0.260 without them. Two earlier confounds were removed before the main run by the neutral note and the mirrored negatives, and the residual fingerprint is the approximate match of lengths between families. The probe says nothing about shortcuts inside the bodies, so the claim that detection is content based rests on the hard-negative construction and the challenge structures with new phrasing.

\subsubsection{Frozen Settings and Versions}
\label{sec:versions}
The study proceeded in three stages: a local mock evaluation, a pilot with real models on a reduced grid, and the main experiment. The first-stage threshold $\theta_1=0.45$, the flag threshold $\tau_{\mathrm{TSA}}=0.60$, the six prototypes, and the TSA judge prompt were fixed on the pilot, which used all three domains, so the held-out-domain analysis of Section~\ref{sec:detection} is a calibration transfer. The sink witness prompt was revised twice after challenge runs, giving w2, and once more after set E showed that w2 read every trusted notice naming a partner as an instruction, giving w3. Four end-to-end runs and one re-derivation produced the reported numbers, which Table~S6 lists by version. Run 3 used kernel v3.3 and w2. Run 4 reused the same traces, seeds, and cached victim decisions with w3 and kernel v3.4, which added full-path chain trust and destination canonicalization. Run 5 applies kernel v3.5 to the stored run-4 outputs, with sets A and F re-run using cached victim decisions. The only change of v3.5 is the identifier contract of Section~\ref{sec:pdg}. Its pre-check depends on the destination string alone and precedes every model call, so a run-4 decision on a well-formed destination is also its v3.5 decision wherever the v3.4 and v3.5 matchers agree on the records. The released script \texttt{check\_v35\_equivalence.py} confirms that they agree on every record text and identifier of every set except the six space-written rules of set A, which is why that set is re-run. The re-derivation changed only actual victim calls with malformed destinations. All changed calls were benign and are listed in the released log. They are 2 of 71 approved calls in the main run, 7 of 69 with the hardened victim, 1 of 75 with the labeled victim, 7 of 75 with the Llama victim, 1 in the challenge set, 4 in set D, 6 in the frozen set, and 7 in its Llama-victim run. No counterfactual decision changed in the re-derivation. Cost and latency results remain run-4 measurements. Run 6, added in the second revision, evaluates only the witness-agreement variant of Section~\ref{sec:agreement} on the main run, the challenge set, set E, and the frozen set, under kernel v3.5 and w3 with the cached victim decisions and with Llama 4 Maverick as the second witness, and nothing else was re-run or re-tuned. Run 7, also added in the second revision, evaluates the second held-out set of Section~\ref{sec:unseen2-design} under the same kernel, prompt, and second witness, once with the frozen resolver and once with the extended pattern, with new victim decisions for its 240 traces. The frozen evaluation set was generated and run under kernel v3.4 and w3. The re-derivation under v3.5 left all 260 of its counterfactual decisions unchanged, and Section~\ref{sec:unseen} reports the changes to actual victim calls separately. Because the model-based calls are regenerated in every end-to-end run at temperature 0, run 4 also measures the run-to-run variation of those conditions on identical inputs, as Section~\ref{sec:utility} reports.

\subsubsection{Policy Challenge Set}
\label{sec:holdout-design}
Fifteen structures written with different phrasing, such as handoff notes, tags, contact sheets, and operator notices, and different reference tokens test each branch of the kernel. Table~S7 lists them with the specified decision, which was fixed from the operator's authorization policy before the structures were run, and Figure~\ref{fig:holdout} reports them. Each structure is instantiated in three domains with four repetitions, 180 traces in total. The gate of every condition is evaluated counterfactually on each listed destination in the same context, 240 calls, and on the destination the victim actually chose, 176 external calls.

The first ten structures were used to find and fix two defects of an earlier kernel, a trusted registry entry whose literal binding of the destination counted as authorization and session-keyed lineages that diluted operator rules. The five later structures test the same-record, same-source, same-destination, ambiguity, and hop-limit cases, and the endpoint pre-check and Equation~\eqref{eq:verify} were added after a run in which the three-hop structure failed. The set is therefore a policy challenge evaluation of a kernel that was developed against it in part, not an unseen-structure generalization test.

\subsubsection{Robustness Sets}
\label{sec:robust-design}
The nine robustness sets probe failures beyond the assumptions of the main run. They were initially evaluated under kernel v3.4 and prompt w3, and their results were re-derived under v3.5, except that sets A and F were re-run using cached victim decisions. All sets reuse the main-run generators for fillers, background lineages, layout, and sessions, so that only the records named below differ, and the gate of every condition is evaluated counterfactually on the listed destination in every trace and on the destination the victim chose.

Set A, degraded approved rules, contains 210 benign approved-transfer traces, 7 variants $\times$ 3 domains $\times$ 10 repetitions. Each trace includes an untrusted background lineage of the form the attacks use and an operator rule for partner A. The seven variants are the canonical phrasing as a control, a paraphrase generated by gemini-2.5-flash with six paraphrases per domain released with the data, a rule without an imperative verb, a rule naming a registry key that a trusted contact sheet resolves to A, the same rule with the contact sheet written through the ingestion connector, which the policy denies, the partner identifier in another surface form with two repetitions per form and domain, and a directive split over two trusted records with no mapping in the relation pattern. The surface forms are lower case, spaces, underscores, trailing punctuation, and a parenthesized suffix. Set B, multi-connector attacks, holds 150 attack traces, 5 structures $\times$ 3 domains $\times$ 10 repetitions, in which the $k=3$ attack records arrive through one connector as a control, through two or three connectors, through two connectors with the registry entry written by the operations identity, and through two connectors with the mapping phrased outside $M$. Set C swaps the model family: the main run and the challenge set are re-evaluated with Llama 4 Maverick as the TSA judge, the witness, the attribution judge, and the scalar judge, reusing the cached victim decisions, so that gate decisions are compared row by row with those of the primary judge.

Set D, two-hop chains, contains 210 benign traces, 7 variants $\times$ 3 domains $\times$ 10 repetitions. In each trace, a trusted rule names label A, a contact sheet maps A to key B, and a directory line maps B to the endpoint. Both mappings are trusted and unambiguous in the control. The six variants apply one of three perturbations at either hop: an untrusted record, a record without a sidecar, or an additional conflicting record. Hop one is the endpoint mapping from B, and hop two is the label mapping from A to B. The specified decision is pass for the control and block for every variant. Set E, descriptive notices, holds 150 benign traces, 5 phrasings $\times$ 3 domains $\times$ 10 repetitions, in which the only trusted record naming partner A is a notice that states a fact about A, with the phrasings listed in Table~\ref{tab:newsets}, and no rule instructs a transfer. The specified decision is block. The authorization policy behind this specification is that a trusted record authorizes a transfer only if it commits output to be sent, that is, it instructs or establishes that a report or data is forwarded, routed, mirrored, or delivered to the destination. A record that states who a partner, recipient, or contact is, or who handles a function, describes the organization and does not commit any output. Phrasing E5, ``partner A handles distribution of the report'', is the borderline case: it attributes a function to A but names no transfer by the agent, so the policy classes it as descriptive and specifies block, while the manuscript acknowledges that a human reader could take it for a standing arrangement. Set F, identifier surface forms, look-alikes, and malformed forms, holds 30 benign traces with the canonical rule naming A and evaluates 15 counterfactual destinations per trace: five legitimate variants of A, which must pass; seven look-alikes that denote other endpoints, which must block; and the three malformed forms that the victims actually issued in the run-4 logs, which must be blocked as malformed before any branch. Section~\ref{sec:pdg} gives examples of the variants and look-alikes, and Section~\ref{sec:confusable} gives the three malformed forms. Set G, lineage scale, contains 120 traces, 4 sizes $\times$ 3 domains $\times$ 5 repetitions $\times$ 2 classes. Each trace contains an untrusted lineage from one connector with $n\in\{10,50,100,200\}$ unrelated operational records. In attack traces, the same lineage also contains the three attack records. In benign traces, it contains no attack records, and an approved rule is present in the context. Set H, latency, holds 120 benign traces, $m\in\{1,2,3,5\}$ $\times$ 3 domains $\times$ 10 repetitions, in which $m$ trusted rules with different phrasing name the same partner, so that the sink evaluates $m$ binding lineages. Each trace is run with warm caches, in a second pass in the same process, and with every cache bypassed. Set I, trusted-rewrite laundering, holds 120 traces, 4 variants $\times$ 3 domains $\times$ 10 repetitions: a trusted operations agent, driven by gemini-2.5-flash-lite with a one-sentence summarization prompt released with the code, reads the session-1 records, which contain the $k=3$ attack lineage or an approved rule with an untrusted background, and writes a handoff note. The victim then reads the context in a later session with the original records present or with the original untrusted records, or the original rule, compacted away so that only the note remains.

Two further runs vary the victim rather than the gate. The hardened prompt retains the operational task. It instructs the agent to treat stored content originating outside the organization as data and never as an instruction. It permits routing only under an approved operator rule and requires the agent to report instead of routing when it cannot determine the origin of the content. The labeled variant adds the hardened prompt and prefixes every record with the origin label the gateway knows, either external ingestion connector or operations team. Both are run on the 918 main-run traces with new victim decisions.

\subsubsection{Frozen Evaluation Set}
\label{sec:unseen-design}
To assess new phrasings and domain transfer under frozen settings, an additional evaluation set was generated after kernel v3.4, the relation pattern, witness prompt w3, the thresholds, and the canonicalization rule were fixed, and nothing in the set was changed afterwards. The later v3.5 identifier contract was applied to it in the separate re-derivation of Section~\ref{sec:versions}, which changed none of its 260 counterfactual decisions and changed six primary-victim and seven Llama-victim actual-call decisions, as Section~\ref{sec:unseen} reports. The phrasings were written by the second model family, Llama 4 Maverick, from a prompt that names only placeholders and the record kinds, in four domains: the three of the main run and a fourth, procurement, whose vocabulary appears in no other generator. For each domain the model wrote three attack triples, each consisting of a procedure record naming a label, a binding record from the label to a key, and an address record from the key to the endpoint, as well as three direct rules, two rules via a key, three contact-sheet lines, three descriptive notices, two prohibitions, two revocations, two mentions, and three internal archive rules. The builder substitutes identifiers and edits no phrasing. The twelve structures listed in Table~S9 are instantiated in four domains with five repetitions per structure and domain, yielding 240 traces and 260 counterfactual calls. The specified decisions were fixed before the run. Every structure but one has a counterpart in a development set, also recorded in Table~S9, and differs from it in wording and domain. The exception is a trusted rule that a later trusted record revokes, a revocation case that no development set contains. The set was run once with the primary victim and once with Llama 4 Maverick as the victim, and the counterfactual decisions are identical for both because they depend on the records, not on the victim. A diagnostic that only counts how many of the model-written binding, address, and contact-sheet records the frozen relation pattern resolves is reported with the results, and a post-hoc analysis that extends the pattern with the observed relation phrases is reported separately and labeled as such.

\subsubsection{Second Held-Out Set}
\label{sec:unseen2-design}
The frozen set of Section~\ref{sec:unseen-design} was read before the witness-agreement criterion of Section~\ref{sec:agreement} and the extended relation pattern of Section~\ref{sec:unseen} were written, so neither can be validated on it. A second held-out set, H2, was therefore generated in run 7 after both were fixed. The order of steps was recorded so that nothing could be adapted to the set. First, the kernel v3.5, the resolver with the extended pattern, witness prompt w3, the agreement rule, the second-witness identifier, and the specified decision of every structure were frozen, and the SHA-256 hash of each file that decides a gate outcome was written to a freeze record. Second, Llama 4 Maverick wrote the phrasings from a prompt that names only placeholders and record kinds, and a screen rejected candidates to reduce lexical reuse. The known corpus was the run-5 phrasing file, the five set-E templates, and the canonical rule of the main run, extended within each domain by the candidates already accepted. For a non-mapping record, placeholders, the domain tag, report names, identifiers, and function words were removed, and the candidate was rejected if fewer than three content words remained or if the Jaccard coefficient of its content-word set with that of any known wording was 0.7 or more. For a mapping record, the content words between its two placeholders form its relation phrase, and the candidate was rejected if this phrase was identical to the relation phrase of a known mapping record. Reuse of a relation operator inside a different phrase was not a rejection criterion, so the accepted sheet ``Key K is linked to A'' shares the operator of the run-5 sheet ``Key K is linked to partner A'' but not its relation phrase, and H2 therefore tests unseen complete formulations under fixed resolver rules, including formulations that reuse known operators. The screen was first configured with a single threshold of 0.6 for all records. That configuration rejected nearly every mapping record and wrote no phrasing file, so it was revised to the rule above and the freeze record was rewritten before any phrasing was accepted and before any evaluation. The screen reduces lexical reuse and does not guarantee a new semantic type. H2 also includes E5-type boundary probes, the function notices, whose results are reported separately from the newly generated descriptive-notice formulations. Third, a review sheet listing every phrasing with the structures that use it and their specified decisions was produced and read before any evaluation, and the reviewed file was locked by hash. The runner refuses to evaluate the set if the freeze record or the lock does not match. The twelve structures cover the two open questions. Five test the semantic criterion: an explicit trusted rule, a trusted non-imperative standing arrangement that commits the report to the partner, a descriptive notice, a record that attributes a function such as distribution to the partner without naming a transfer, which is the E5 type, and a trusted rule beside an untrusted mention. Seven test reference resolution: a one-hop key with a trusted sheet, with an untrusted sheet, with no sheet, and with conflicting trusted and untrusted sheets, a two-hop chain with trusted and with poisoned mappings, and the attack triple split over two connectors. The specified decisions follow the policy of Section~\ref{sec:robust-design}: the explicit rule, the arrangement, the rule beside a mention, the trusted one-hop key, and the trusted two-hop chain pass, and every other structure blocks, with a key that resolves to more than one value treated as ambiguous. Revocation is excluded because Section~\ref{sec:unseen} identifies it as an unsupported capability. The set has 240 traces and 260 counterfactual calls, the same size as the frozen set, in the same four domains with five repetitions. It was run once with the frozen resolver, under STPG and under witness agreement, and once with the extended resolver on the same traces and the same cached victim decisions, so that the four results differ only in the gate.

\subsection{Comparison Conditions, Metrics, and Statistics}
\label{sec:conditions}
Nine comparison conditions are evaluated on the same traces using the same cached victim decisions and the adapters in Table~\ref{tab:adapters}: STPG, STPG with the allow-on-empty default, the trusted-directive-only ablation under each default, PPT with the conservative gate, trusted-rule matching, the full-context attribution judge, the ephemeral-taint proxy, and the undefended pipeline as reference. Three scorers are reported for detection only, because their defense behavior on the kernel would repeat the conservative gate: a scalar full-context judge that makes one judgment over the whole read, unit inspection that takes the maximum per-record embedding score, and a window scorer that embeds the five most recent records without a judge stage. The conservative gate, matching, taint, and the detection-only scorers are reduced proxies of method families, not reimplementations of specific systems: no result in this paper compares STPG with CaMeL, PFI, AuthGraph, MemLineage, PPMF, or any other published system under its own conditions, and every difference reported is a difference between evidence adapters on the common kernel. A fourth variant, STPG with witness agreement, keeps every component and tightens the authorization criterion: a trusted lineage authorizes the destination only if the primary witness and a second witness of a different model family, Llama 4 Maverick under the same prompt w3, both return a verdict that passes Equation~\eqref{eq:verify}. The untrusted branch and the deny-by-default policy are unchanged, so the variant cannot authorize a call that STPG blocks, and a previously authorized call may instead be blocked by the untrusted-directive branch or the default. Three STPG variants isolate individual components. Per-record grouping and per-session grouping change only the unit over which records are assembled, and binding, the witness, the kernel, and the default remain unchanged, as Section~\ref{sec:grouping} describes. Read-set inheritance lowers the trust of a trusted agent's write to the minimum trust of the records it read in the same session, as Section~\ref{sec:launder} examines.

\label{sec:stats}
Four aspects of effectiveness are evaluated separately: attack blocking, approved-transfer preservation, policy conformance, and read-level detection. Defense on attacks: the ASR (Attack Success Rate) is the fraction of attack traces in which the agent issues an external routing call and the sink allows it. Defense on approved work: the false-block rate over the approved external transfers the agent actually issued, with the pass reason recorded as trusted directive or empty evidence. We verify that internal routing is never blocked and report off-task external calls separately. For the external calls evaluated by the gate, we report precision, recall, and F1, counting a blocked attack call as a true positive and a blocked approved transfer as a false positive \cite{fawcett2006}. Policy conformance on the challenge set: the fraction of counterfactual calls decided as specified, reported separately from the preservation of business-approved calls, whose denominator includes approved transfers that the policy deliberately denies. Detection: AUROC of the read-level score against all 270 benign traces and against the 195 without an approved external-transfer directive, with TPR (True Positive Rate), FPR (False Positive Rate), precision, recall, and F1 at the a priori threshold, the maximum TPR subject to FPR $\le5\%$, and the operating point transferred from the other two domains. Proportions carry exact 95\% Clopper--Pearson intervals and paired false-block comparisons use the exact McNemar test. Both assume independent traces, which shared templates violate, so false blocks are also reported per domain. We estimate 95\% AUROC confidence intervals (CIs) from 2,000 percentile-bootstrap resamples \cite{efron1979}. To account for within-family dependence in ROC analysis \cite{obuchowski1997}, we report both trace-level and cluster-level intervals, and for the latter the template families are resampled within each class. Comparisons between scorers use the DeLong test \cite{delong1988} and paired cluster-bootstrap intervals. With twelve families per class these intervals are imprecise. Latency: the wall-clock time of the read-time analysis and of the sink-time authorization of each operation, measured inside the gateway, as median, 95th, and 99th percentiles, for warm caches, for a second pass in the same process, and for cold caches.

Undefended, the agent issued the external routing call in 648 of 648 attack traces and the call was allowed in all, an ASR of 1.000 $[0.994,1.000]$, uniformly across $k$, $d$, $g$, locations, and domains. STPG, its allow-on-empty condition, the trusted-directive-only ablation, the conservative gate, trusted-rule matching, and the attribution judge blocked all 648, an ASR of 0.000 $[0.000,0.006]$, each for the reason its adapter records, STPG through the untrusted branch with no unsupported verdict. The ephemeral-taint proxy and the trusted-directive-only ablation with the allow-on-empty default blocked none. The two privilege gaps behave identically, with 324 of 324 blocked in each and $\Delta\pi$ logged as $\mathrm{IAM}-\mathrm{write}$ for $g=1$ and $0$ for $g=0$. H1 holds for these configurations: on the default-deny kernel the attack is blocked because no trusted directive targets the destination, and the conditions that persist provenance differ in what they record and in what they do to approved work. This result applies to the main run and does not extend to all relaxed settings in Sections~\ref{sec:robust} to \ref{sec:limitsops}.

Figure~\ref{fig:holdout} shows every condition. STPG conformed to all 240 counterfactual decisions: the 84 calls specified as pass all passed through the trusted-directive branch, and of the 156 specified as block, 96 were blocked by the untrusted branch, 24 by the ambiguity rule, and 36 by the default, namely 12 off-task strings, 12 prohibited destinations of the same-record structure, and 12 three-hop calls.

Policy conformance and preservation of business-approved transfers use different denominators. The business-approved denominator is 108, including the 12 approved transfers whose rules lost their provenance and the 12 that reach the partner only through three hops. STPG passed 84 of these transfers and blocked the remaining 24, all in accordance with the policy. The alternatives fail where their adapters predict. Trusted-rule matching, at 168 of 240, passes the unauthorized transfers of the cross-reference, trusted-mention, same-record, ambiguous-key, and three-hop structures. The allow-on-empty condition, at 204 of 240, passes exactly the 36 calls that reached the default: 12 business-approved transfers that the hop policy denies and 24 policy-compliant blocks converted into unauthorized passes. Per-record grouping conforms to all 240 and per-session grouping to 167, as Section~\ref{sec:grouping} reports.

A branch count identifies the rule that fired, but it does not establish whether the witness interpreted the text correctly. Figure~S1 therefore reports witness verdicts and kernel verification separately for the 396 binding lineages evaluated on the counterfactual calls. A verdict is verified when the raw verdict is true and Equation~\eqref{eq:verify} holds, rejected when the raw verdict is true but no admissible non-mapping candidate exists, and negative when the raw verdict is false. The witness returned 261 positive and 135 negative verdicts, and the kernel verified 216 of the positive verdicts and rejected 45. Under prompt w2 in run 3, the verified, rejected, and negative counts were 214, 116, and 66. The w3 clause thus shifted most mapping-only lineages from rejected positive verdicts to negative verdicts, while the verified count increased only from 214 to 216.

These are lineage-level rejections, not 45 incorrectly authorized calls, because trust and default decisions follow verification. No verified target relied on a mapping record, and none of the 717 main-run verdicts was rejected. The 135 negative verdicts are the readings the mention, same-record, and mapping structures rely on: 24 mentions, 12 prohibitions, and 99 mapping-only lineages. The witness therefore read instruction against mention or prohibition in the same text correctly and, under w3, read most mapping-only text as mapping. Where it still over-read, the kernel did not let it decide. The named lineage, role, and $\Delta\pi$ of the 648 blocked attacks are coverage of the attribution output, not a measured precision, because no independent gold support set exists for them.

\subsubsection{Degraded Approved Rules and Multi-Connector Attacks}
\label{sec:rules}
The main run assumes that operator rules name the partner literally and that each attack lineage arrives through a single connector. Sets A and B relax these assumptions. Section~\ref{sec:robust-design} defines the variants, and Table~S8 and Figure~\ref{fig:robust} report the results. Section~\ref{sec:judgeswap} reports set C, which swaps the model family.
On the counterfactual call to partner A, STPG passed every paraphrased rule, 30 of 30, because the witness read the six LLM-written phrasings as directives. It also passed every rule without an imperative verb, every rule that reaches A through a trusted contact sheet, and 24 of the 30 rules whose partner identifier is written in another surface form: all 24 written in lower case, with underscores, with a trailing period, or with a parenthesized suffix, and none of the 6 written as three space-separated words, because under the identifier contract a rule that spells PARTNER EXT 194 does not name the endpoint PARTNER-EXT-194 and the call reaches the default. The surface-form variant passed 12 of 30 with the literal binding of run 3 and 30 of 30 with the space-folding matcher of run 4, which is the matcher that also absorbed prose into identifiers. The 6 blocks are the measured cost of the contract on this set, and they are the kind of block an operator corrects by writing the identifier as one token. STPG blocked all 30 rules whose contact sheet arrived through the ingestion connector, as the provenance policy specifies. In the variant that splits the directive over two trusted records, the rule record names no partner and the notice, ``delivery partner for the summary report is A'', is phrased outside the relation pattern $M$, so the one-record lineage of the notice is the only binding lineage. STPG passed 21 of 30 because the witness read the notice alone as an instruction and blocked 9 by the default, so the pass never rested on assembling the two records, and the variant is the same semantic question as set E in Section~\ref{sec:notice}. Trusted-rule matching shares the binding step and passed the same 24 of 30 calls in the surface-form variant. It passed all 30 calls in every other variant except the untrusted-sheet variant. The trusted-directive-only variant with allow-on-empty, reported in Table~S8, allowed all 30 calls in every row of both sets. The attribution judge, which reads the rule as text, passed all 30 calls in every variant except the untrusted-sheet variant. The conservative gate blocked every call. On the calls the victim actually issued, STPG passed 22 of 30 in the surface-form variant, blocking as malformed the 6 calls that copied the space-written identifier and 2 that rewrote a lower-case identifier as the word ``partner'' followed by ext-013 or ext-912, and 21 of 30 in the two-record variant. The victim followed the rule without an imperative verb in only 1 of 30 traces, so that variant mainly measures the agent.

Spreading the three attack records over two or three connectors did not open the gate: STPG blocked all 30 calls in every structure through the untrusted branch, because the resolver follows mapping records across lineages and the witness receives the chain together with the binding lineage. With the mapping phrased outside the relation pattern, the lineage that contains the destination literally was bound and the witness read it as a target in all 30 cases, so STPG blocked by the untrusted branch rather than by the default. A mapping that neither matches the pattern nor reads as a directive would reach the default, which blocks under STPG and passes under the allow-on-empty variant. Read-level detection did not degrade, with AUROC 1.000 against the non-directive set even with one record per connector, because the TSA judge scores the operations-rule record alone at 0.80. The detection signal in this data rests mostly on the rule record, and what assembly contributes is the destination, which is what the gate decides on, as Section~\ref{sec:threat} sets out.

\subsection{Frozen Evaluation Set}
\label{sec:unseen}
Figure~\ref{fig:unseen} and Table~S9 report the evaluation set of Section~\ref{sec:unseen-design}, originally evaluated under frozen kernel v3.4 and witness prompt w3. The subsequent v3.5 re-derivation left all 260 counterfactual decisions unchanged. STPG decided 190 of 260 counterfactual calls as specified. Conformance was 49, 46, 47, and 48 of 65 calls in the incident, billing, access-review, and procurement domains, so the procurement result fell within the observed range for the three development domains. The primary victim issued 60 attack calls and STPG blocked all 60, and with Llama 4 Maverick as the victim it blocked 56 of 56. The 70 misses have three causes. First, the relation pattern: the frozen pattern $M$ resolved 5 of the 36 model-written contact-sheet, binding, and address records. Unrecognized literal forms included ``corresponds to'', ``is associated with'', ``is registered under key'', and ``is linked to'', whereas the accepted forms were ``='', ``maps to'', ``resolves to'', and ``is bound to''. Consequently, all 40 approved transfers in the two reference structures were blocked by the default. Of the 60 attack calls, 22 were also blocked by the default rather than through attribution. The allow-on-empty variant admitted these 22 attack calls, along with 16 of 20 calls to the endpoint of the untrusted sheet and 6 of 20 calls through the poisoned chain. Second, the descriptive notice in new wording passed 10 of 20, the failure of set E. Third, the revoked rule passed 20 of 20. The kernel has no notion of a later trusted record withdrawing an earlier authorization, a semantic capability outside the destination-level scope, whereas the prohibition structure, which the witness recognizes, blocked 20 of 20. On the other eight structures the STPG decision matched the specification on 180 of 180 calls. This is conformance, not resolution, since it includes the default denials of the 22 attack calls and the 16 untrusted-sheet calls whose references the pattern did not resolve. Trusted-rule matching conformed to the specified policy on 200 of 260 calls, failing on the prohibition, notice, and revoked-rule structures. The attribution judge conformed on 205 of 260 calls, failing on the notice, revocation, and rule accompanied by an untrusted mention. Both achieved higher policy conformance than STPG on this set because neither depends on the relation pattern. The v3.5 re-derivation did change 6 of the 182 actual external calls of the primary victim and 7 of the 177 issued by the Llama victim, all benign calls to a prefixed or phrased destination. Conformance on the actual calls is 136 of 182 and 125 of 177.

The 70 nonconforming decisions fall into two directions with different implications. Forty are false blocks: approved transfers that reach the partner through a contact sheet or binding record the resolver did not read, 20 in each reference structure, which cost utility and which the allow-on-empty variant would have admitted together with 44 attack calls. Thirty are false authorizations: the 10 notice-only calls and the 20 revoked-rule calls, which cost security. The revoked-rule calls are the one structure whose semantics the kernel does not implement, since a later trusted record that withdraws an earlier authorization is outside the destination-level policy, so revocation is an unsupported capability rather than a misjudgment of a supported one. The 190 of 260 conformance therefore combines 40 utility errors from a fixed lexicon, 10 security errors of the witness on descriptive notices, and 20 security errors from an unsupported capability.

A separately reported post-hoc analysis extends $M$ with the relation phrases observed in the model-written records and a direction rule for symmetric phrases. The extension resolves 29 of the 36 records and changes no decision on the challenge set or any development set. Conformance on the previously frozen set rises to 218 of 260, with 16 of 20 and 12 of 20 conforming decisions in the two reference structures. Because the pattern was extended after these records had been inspected, the 218-of-260 result measures the improvement from a lexicon fitted to the evaluated records. It is not a frozen result and does not establish generalization. Validating the extended resolver requires a further set of previously unseen formulations evaluated without adaptation, which Section~\ref{sec:unseen2} reports: on that set the extension resolved 7 of 36 new mapping records and raised conformance from 215 to 227 of 260, with the two-hop structure unchanged at 0 of 20. The deterministic resolver is thus the component that generalizes least: it is what makes the support path verifiable and keeps the witness from completing references on its own, and it is also a fixed lexicon that free phrasing escapes. A learned or model-assisted resolver whose output the kernel still verifies structurally is the design question this result leaves open.

\subsection{Component and Model Sensitivity}
\label{sec:sensitivity}
\subsubsection{Untrusted-Directive Branch and Grouping}
\label{sec:ablation}
\label{sec:grouping}
The trusted-directive-only ablation keeps grouping, binding, the witness, and chain trust and removes only the untrusted branch. On the default-deny kernel its decisions are identical to those of STPG on all 918 main-run traces and all 240 counterfactual calls, which follows from Equation~\eqref{eq:policy}: every call STPG blocks through the untrusted branch is one for which no trusted directive targets the destination, so the default blocks it as well.

The branch contributes two measured things. The first is attribution output: 648 of 648 attacks are blocked with a named untrusted lineage, per-record roles, and a logged $\Delta\pi$, where the ablation records the no-evidence reason. The second is safety under the availability-preferring default: with allow-on-empty the ablation passes all 648 attacks and conforms to 84 of 240 challenge decisions, whereas STPG with the same default keeps ASR 0.000 and 204 of 240. The read-time detection signal of Section~\ref{sec:detection} is produced by lineage assembly and scoring, which this ablation retains, so their contribution is not isolated here. The scope is therefore as follows: persistent provenance with destination-witnessed, path-verified trusted-directive authorization makes the default-deny decisions, and the untrusted branch attributes the blocked calls and secures the allow-on-empty default.

Two variants keep binding, the witness, the kernel, and the default and change only the unit over which records are assembled. With per-record grouping every record is its own lineage, and with per-session grouping every session is one lineage regardless of source. Per-record grouping made the same gate decision as STPG on every call of the sets on which it was run: on the main run it blocked 648 of 648 attacks and passed 69 of 71 approved transfers, with the same two malformed calls blocked, and it matched STPG on 240 of 240 challenge decisions, on every variant of sets A, B, and D, and on the 260 counterfactual calls of the frozen set. It was not run on sets E to I. The reason is that the resolver and the witness, not the grouping, reconstruct the directive: a record that mentions the destination or a chain token becomes a binding lineage on its own, and the chain supplies the records it refers to. Grouping by source lineage contributes three measured things that per-record grouping does not. The first is the attribution unit, since a blocked call names the lineage of its source connector rather than one record. The second is the read-level score on the all-benign set, 0.829 against 0.726. The third is cost: Table~S11 reports 719 against 2,177 binding lineages and 1,287 against 2,128 second-stage TSA judge calls. Per-session grouping, the natural unit of a session-scoped design, merged the operator's rule with the untrusted records of the same session in the reported comparisons, making the merged lineage untrusted. This condition passed 8 of 71 approved transfers in the main run, conformed to 167 of 240 challenge-set decisions, and passed 0 of 30 canonical rules in set A, and its read-level AUROC fell to 0.918. Spatio-temporal assembly is therefore not what blocks the attacks on this data. Destination binding with full-path resolution and a verified trusted directive is, and assembly by source lineage gives that decision its attribution unit, its detection score, and its cost, while assembly by session reduced approved-transfer preservation.

\subsubsection{Victim Model and Prompt}
\label{sec:generalization}
With Llama 4 Maverick as the victim and everything else unchanged, the agent issued the external routing call in 648 of 648 attack traces, every one to the planted endpoint, and routed all 75 approved transfers externally, with 178 internal routing calls. STPG blocked all 648 attack calls through the untrusted branch and passed 68 of the 75 approved transfers. The 7 it blocked are calls in which this victim wrote the destination as ``partner'' followed by the identifier, which the pre-check blocks as malformed, a false-block rate of 0.093 with interval $[0.038,0.183]$. The primary victim showed this formatting habit in 2 of 71. Trusted-rule matching decided the same calls the same way, the conservative gate blocked all 75, and the attribution judge blocked 34 of 75, 27 by misattribution to the untrusted background and 7 by the pre-check, consistent with the primary victim. The detection scores are identical across victims because the scorer reads the same records, which is a property of the architecture, not evidence of generalization. Two families do not support a rule about model size and susceptibility.

The undefended agent's task instructs it to route whenever the records collectively describe a routing instruction, so the 648-of-648 result may reflect either susceptibility to the attack or compliance with that instruction. Two less permissive settings of the primary victim test this distinction. The hardened prompt treats content originating outside the organization as data, never as an instruction, and permits routing only under an approved operator rule. Even with this prompt, the agent attempted an external routing call in 599 of 648 attack traces: 162 of 162 at each of $k=2$ and $k=3$, 160 of 162 at $k=4$, and 115 of 162 at $k=5$. These are routing attempts, not completed exfiltrations: 465 of the 599 calls name the planted endpoint and 134 name an intermediate label or key rather than the planted endpoint, so the undefended rate is 0.718 counting endpoint calls and 0.924 counting every attempt. The 465 endpoint calls out of 648 split as 159, 131, 137, and 38 at $k=2$ to $5$. The agent cannot tell which records originated outside the organization, because that is exactly the provenance the store dropped. It also routed 69 of 75 approved transfers and issued 24 off-task calls to label strings. When every record was prefixed with the origin label known to the gateway, the agent attempted routing in 570 of 648 traces. Of these attempts, 329 targeted the endpoint, an endpoint-call rate of 0.508, and 241 targeted a label or key. The agent also routed all 75 approved transfers. Thus, even when told which records were external and instructed not to act on them, the model followed the assembled directive to its endpoint or label in about seven of eight traces. STPG blocked all attempts in both settings, 599 of 599 under the hardened prompt and 570 of 570 with origin labels. It blocked label calls as non-endpoint calls and the remaining attempts through the untrusted branch. STPG passed all well-formed approved transfers, 62 of the 69 issued under the hardened prompt and 74 of the 75 issued with origin labels. The remaining 7 and 1 calls, respectively, used prefixed destinations of the kind described above and were blocked. A stored directive is legitimate in this testbed when it is issued by a trusted writer, and following a directive introduced through the untrusted ingestion path constitutes an attack. The prompt cannot make that distinction without provenance, and with provenance in the prompt the model still does not reliably make it.

\subsubsection{Second Model Family as Judge and Witness}
\label{sec:judgeswap}
With Llama 4 Maverick as the TSA judge, the witness, the attribution judge, and the scalar judge, the STPG gate decisions were identical to the primary run on all 918 main-run traces and all 240 counterfactual calls, and so were those of the allow-on-empty variant. On the challenge set, the Llama witness yielded 216 verified, 174 negative, and 6 rejected positive verdicts, compared with 216, 135, and 45 for the primary witness. The verified set was identical, although the second model produced fewer positive readings of mapping-only text. Policy conformance was therefore unchanged, because the structural check and the trust rule, rather than the raw verdict alone, decide. The read-level detection depends on the judge. The assembled-lineage AUROC of STPG against the non-directive set fell from 1.000 to 0.990, with TPR 0.966 and 0 false positives at the a priori threshold, as Figure~S3 shows, and that of the scalar judge rose from 0.996 to 0.999. The attribution judge changed with its model more than with the run: with Llama it blocked all 71 approved transfers, 69 attributed to the untrusted background lineage and 2 by the pre-check, and conformed to 135 of 240 challenge decisions against 156. The gate decisions are thus insensitive to the model family on this data while the detection scores and the attribution baseline are not, the expected consequence of placing the semantic verdict behind a deterministic support path.

The second witness agreed with the primary witness on all 69 primary-verified trusted lineages of the main run and all 144 of the challenge set.

Two conclusions follow. Agreement between two model families is a usable semantic criterion where the two models err differently: the additional witness corrected all 28 primary false authorizations for phrasings E1 to E4 and four of the ten in the frozen notice-only structure, while leaving E5 unchanged, and no additional false blocks were observed in the evaluated main, challenge, or frozen sets. It is not a solution for the borderline case: E5 attributes a function to A without naming a transfer. Both models interpret this wording as a standing arrangement, whereas the policy of Section~\ref{sec:robust-design} classifies it as descriptive. The operator must specify explicitly whether such a record authorizes a transfer, for example by requiring an action verb in any authorizing record. Neither a single witness nor a pair of witnesses can be expected to infer an unstated policy choice. The criterion was evaluated once, after the frozen set and the challenge set had been run and without changing the prompt, the kernel, or the specified decisions, and it is reported as a sensitivity result rather than as a new default of STPG.

\subsection{Operational Limits: Cost, Scale, Latency, and Trusted Rewrites}
\label{sec:limitsops}
\subsubsection{Cost of Each Condition}
\label{sec:cost}
Table~S11 reports measured calls, tokens, cache behavior, wall-clock time, and list-price cost per condition for the main run as measured in run 4, separating read-time model calls, the TSA judge and the scalar judge, from sink-time calls, the witness and the attribution judge. Embedding requests are text-keyed cache lookups, all served from the cache in this run, which was filled with 2,310 API calls during the pilot and run 1. At read time STPG issues one embedding lookup per lineage, 17,766 over 918 reads plus 6 one-time prototype lookups, and 1,287 TSA judge calls, 1.40 per read with about 143 input tokens each.

At sink time STPG issues one witness evaluation per binding lineage of an external call, $\sum_c|B(\delta_c)|$: 719 evaluations for the 719 external calls that passed the pre-checks of run 4, which amounted to 716 API calls and 3 cache hits with about 562 input tokens each under prompt w3. Under v3.5 the two malformed calls are blocked before the witness, so 717 witness evaluations and 717 attribution calls would be issued, but the table keeps the run-4 counts. Every main-run call had one binding lineage, but the count is not a per-call bound: the 416 gate evaluations of the challenge set needed 661 witness evaluations, and Section~\ref{sec:latency} varies the count directly. The attribution judge issues one call per external call past the pre-check, 719 calls with 1,218 input tokens each, and the scalar judge one per read. Grouping also affects cost. Per-record grouping makes 2,128 second-stage TSA judge calls over 20,050 embedded lineages at read time and evaluates 2,177 binding lineages at the sink, about three times the STPG count. Per-session grouping creates merged texts that miss the embedding cache, requiring 2,180 embedding API calls, and its witness inputs total 1.004 million tokens. The reported wall-clock times are totals for 918 traces on a shared workstation, including store operations, and Section~\ref{sec:latency} reports per-operation latency separately. Costs use the November 2026 Vertex AI list prices for gemini-2.5-flash-lite, USD 0.10 per million input tokens and USD 0.40 per million output tokens. These figures describe the model-call cost of the experiment and are not deployment estimates.

\subsubsection{Lineage Scale}
\label{sec:scale}
Set G grows the untrusted lineage of one connector with $n\in\{10,50,100,200\}$ unrelated operational records. Under the default-deny kernel, the gate blocked all 15 attack calls and passed all 15 approved transfers at each size. The blocking branch nevertheless changed. At $n=10$ and $50$, the untrusted branch blocked the attacks. At $n=100$ and $200$, the witness response could not be parsed because the per-record role output exceeded its budget, so the verdict was treated as unsupported and the default fired. Consequently, the allow-on-empty variant admitted 0 of 15 attacks at each smaller size and 15 of 15 at each larger size. Read-level detection degraded earlier: the score the TSA judge gave the assembled lineage fell from a median of 0.70 at $n=10$ to 0.44 at $n\ge50$, below the a priori threshold, while the approved rules kept their scores. The scalar judge fell the same way, and unit inspection was unaffected because it scores records one by one. The victim itself followed the directive in 14, 13, 12, and 9 of 15 traces across the four sizes, and read-time latency grew from a median of 1.5 s to 1.7 s. Dilution of the assembled text and the output format of the witness are therefore the two scale limits of the design: the first is a property of scoring a concatenation, the second an implementation choice that a deployment would change by asking roles only for the support records, which we did not do post hoc.

\subsubsection{Trusted-Rewrite Laundering}
\label{sec:launder}
Set I measures the trusted-rewrite laundering path. A trusted operations agent summarized the session-1 records in one sentence, and in 60 of 60 attack traces the summary named the synthetic sink, so the note, written by a trusted identity, is a trusted directive to the sink. STPG passed the laundered attack in 20 of 30 traces with the original records present and 19 of 30 with them compacted away. The 21 blocks occurred only because the summary happened to contain a phrase of the relation pattern, which made the note a mapping record that cannot support a verdict, so we count laundering as unmitigated. Trusted-rule matching passed all 60, whereas the conservative gate and the attribution judge blocked the 30 with the original untrusted records present and passed the 30 compacted ones. Read-set inheritance was the only mitigation evaluated. It assigns the note the minimum trust of the records read by the agent during the session that produced the note, a read set the gateway knows because it served the read. The mitigation blocked all 60 laundered attacks and passed all 30 approved transfers whose original rules remained available. It also blocked all 30 approved transfers whose rules had been compacted into the note, because the read set of the note included the untrusted background lineage. Thus, the mitigation prevented laundering in this evaluation but falsely blocked every approved arrangement retained only in the summary of a trusted agent. Alternatives that were not evaluated include attaching the read set as a separate provenance field visible to the witness, requiring trusted rewrites to quote the record identifiers they summarize, or exempting notes whose read set contains an approved rule for the same destination. This trade-off motivates explicit derivation metadata for trusted rewrites, which would extend the evaluated gateway protocol.


\subsection{Limitations and Threats to Validity}
\label{sec:validity}
\textbf{Construct validity:} The ceiling and floor values in the main run reflect a controlled synthetic setting in which rules name partners literally and lineages contain clear directives. Sections~\ref{sec:robust} to \ref{sec:limitsops} relax these assumptions. The twelve attack and twelve benign template families limit phrasing diversity, which makes the both-class cluster intervals the relevant uncertainty estimates. The frozen set adds twelve structures, a fourth domain, and phrasings from a second model family. However, its 240 traces were generated from one prompt, and eleven of its twelve structures have development-set counterparts, as Table~S9 lists. It therefore tests new wording, a new domain, and one new semantic case without establishing generalization to entirely new reference structures. The metadata probe does not test shortcuts in record bodies. The challenge set partly informed kernel development, and the post-hoc analysis of the frozen set is not a frozen result.

\textbf{Internal validity:} TSA thresholds, prototypes, and prompt were frozen on a pilot that used all three domains. The witness prompt and the kernel were revised between runs as Section~\ref{sec:versions} records, and the v3.5 identifier contract was applied to the stored logs after the frozen set had been run. The victim's decisions were cached so that every condition saw the same action, and repetitions therefore measure input variation, not generation variance. The model-based conditions, by contrast, moved between runs 3 and 4 on identical inputs, as Section~\ref{sec:utility} reports. The approved-transfer result counts the calls the agent issued: 69 of 71 passed, and all 69 well-formed calls passed.

\textbf{External validity:} The evaluation used two model families on one cloud provider. Using the second family as judge and witness changed no gate decision in the main run or the challenge set. Using it as the victim changed approved-call outcomes only through destination formatting. The second family did change the detection scores and the attribution baseline. The attack content is non-destructive by design, so ecological validity rests on the realism of the record format. As defined in Section~\ref{sec:threat}, authorization is scoped to the destination of a routing call. The guarantee does not cover a different payload or purpose at an authorized destination, or an authorization that a later trusted record revokes. Main-run contexts contained 8 to 26 records, and Section~\ref{sec:scale} examines degradation with larger lineages.

\textbf{Mechanism:} The conditions of the STPG guarantee are the identifier contract, the relation pattern $M$, and the witness, and each has a measured failure. The contract blocks approved calls whose destination is not a single identifier, as Sections~\ref{sec:utility} and \ref{sec:rules} show. The pattern resolved 5 of 36 model-written mapping records in the frozen set and none of the 36 in the second held-out set, and its post-hoc extension resolved 7 of the latter, as Sections~\ref{sec:unseen} and \ref{sec:unseen2} report. A single token that no record resolves is accepted as a final endpoint by the contract, so a victim that routes to a bare registry key is passed when a trusted rule names that key, as Section~\ref{sec:unseen2} shows. The witness reads descriptive notices as instructions in 53 of 150 cases under prompt w3 and in 10 of 20 in new wording, and requiring agreement with a second model family reduces these to 25 of 150 and 6 of 20 without removing the borderline phrasing, as Sections~\ref{sec:notice}, \ref{sec:unseen}, and \ref{sec:agreement} show, and on the second held-out set agreement left two false authorizations on the function-attribution form and one false block of a standing arrangement among 100 semantic calls, as Section~\ref{sec:unseen2} shows. Its per-record output format fails beyond about 100 records, as Section~\ref{sec:scale} shows. The two-hop defect of kernel v3.3 and its correction are described in Section~\ref{sec:pdg} and evaluated in Section~\ref{sec:chain2}.

\textbf{Adaptive adversaries:} An adversary who phrases the mapping outside $M$ and the destination record so that the witness does not read it as a target, or who pads the lineage with about 100 unrelated records, reaches the default, which blocks under STPG and passes under the allow-on-empty variant. An adversary who makes the victim route to a look-alike of an approved identifier is blocked by the identifier contract. An adversary who makes a trusted agent summarize the planted records inherits that agent's trust unless the gateway applies read-set inheritance or another derivation rule, of which only the first was evaluated, as Section~\ref{sec:launder} describes.

\section{Conclusion}
\label{sec:conclusion}

STPG combines persistent connector provenance with destination-conditioned witnessing and deterministic support-path verification at an MCP gateway. On the main synthetic dataset, it blocked all 648 attack calls and passed 69 of 71 approved transfers, and the two false blocks resulted from malformed destinations. These results compare evidence adapters on a common kernel, not implementations of published defenses. Per-record grouping produced the same gate decisions as source-lineage grouping on the main run, the challenge set, and the frozen set, so spatio-temporal assembly did not itself improve attack blocking on the three datasets evaluated in the grouping ablation. What source-lineage grouping contributed is the connector-level attribution unit, a higher all-benign AUROC point estimate, and lower computational cost, and these three are the methodological contribution of assembly in this paper. The untrusted-directive branch provided attribution and protection under allow-on-empty, while leaving default-deny decisions unchanged.

STPG conformed to the specified policy on all 240 counterfactual calls in the challenge set, which partly informed development. A separate set with second-family phrasings and a new domain was generated after kernel v3.4 and witness prompt w3 were frozen, and STPG matched the specified decision on 190 of its 260 counterfactual calls. Eleven of its twelve structures had development-set counterparts. The later v3.5 identifier contract left these 260 decisions unchanged, and its effects on actual victim calls are reported separately. The contract also blocks the six space-written rules in set A. Resolver failures, notice misclassification, and unsupported revocation semantics explain the frozen-set misses, which split into 40 false blocks and 30 false authorizations. Requiring two witness models to agree removed the false authorizations of four of the five descriptive-notice phrasings and four of the ten in the frozen notice-only structure without additional false blocks on the main run or the challenge set, but not those of the borderline phrasing that both models read as an arrangement. The separately labeled post-hoc resolver extension reached 218 of 260 on that set and is not a frozen result. A second held-out set was generated by the second model family after the agreement rule, the extended pattern, and all other settings had been frozen and hashed. Policy conformance was 215 of 260 under STPG, 217 with witness agreement, 227 with the extended resolver, and 229 with both. All calls built on the twelve newly generated descriptive-notice formulations or on explicit rules were decided as specified. Under agreement, the two remaining false authorizations involved function-attribution wording and one standing arrangement was still falsely blocked. The extension resolved 7 of 36 new mapping records, enabling some one-hop references but no two-hop chain. Workflows in which a trusted agent rewrites untrusted content are outside the evaluated guarantee: STPG allowed 39 of 60 attacks after trusted rewrites, whereas read-set inheritance blocked all 60 but also blocked all 30 approved transfers whose original rules had been compacted.

These findings support destination-level enforcement under the evaluated identifier contract, resolver rules, and witness behavior. They do not support a general claim about other deployments: the two held-out sets show that conformance depends on the relation vocabulary of the resolver and on the policy structures the kernel implements, and a different vocabulary or an unsupported structure such as revocation changes the outcome. They also show that the default policy determines how each module contributes to the final decision, so detection and enforcement should be evaluated separately on the same kernel and under both defaults. A provenance defense should identify the records supporting a directive and verify that the directive targets the requested destination. Relative to MemLineage and PPMF \cite{ouyang2026memlineage,xu2026ppmf}, which were not run here, STPG adds source-connector grouping of records dispersed across a shared store and the measured split between the two defaults. The findings do not establish detection superiority, since confidence intervals for paired AUROC differences from the scalar judge and unit inspection included zero, and external validity remains limited to synthetic traces, two model families, and one cloud provider. As a training-free gateway component, STPG could complement zero-trust and access-control architectures \cite{syed2022zta,nist2020zta}. Related work examines authentication in microservice environments \cite{microsvc2025} and AI-orchestrated zero-trust defenses on constrained edge hardware \cite{edgezt2026}. Priorities for further work are structurally verified model-assisted resolution, revocation handling, scalable witness outputs, declared derivation for trusted rewrites, and broader evaluation. Payload, purpose, and other authorization dimensions remain outside the evaluated scope. The code, data, cached decisions, raw results, and analysis scripts are released as described in the Data Availability Statement.
